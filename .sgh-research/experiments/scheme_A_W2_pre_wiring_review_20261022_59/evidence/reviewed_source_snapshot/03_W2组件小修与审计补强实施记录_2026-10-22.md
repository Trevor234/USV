## 2. 组件小修

派生副本：`implementation/w2_gate_v2/`。57 包原件未改。

### 2.1 EINTR 后的累计耗时（§3.1）

`PipeReader::read_some` 现在从**调用入口**记一个 `call_start_ns`，所有返回路径（成功、EOF、超时、EINTR 重试后失败）都通过同一个 `finish()` lambda 报告 `monotonic_ns() - call_start_ns`。

旧实现在成功与普通超时分支只回报**最后一次 poll 的 slice**，先前被信号打断的等待被漏记。58 号补测实测：真实 200.3 ms 的等待只报了 100.1 ms，少记约 100 ms；组合场景下 gate 预算 600 ms 却在 750.4 ms 后仍返回 `released`。

### 2.2 预算改为绝对期限，晚到帧不再放行（§3.1 后半）

`Gate::wait` 不再递减 `remaining`，改为在入口固定 `deadline_ns = now_ns() + timeout_ns_`。每个 slice 只拿 `deadline - now` 与 `kSliceNs`（50 ms）中较小者，所以 partial read 或 EINTR 无法为下一 slice 续一个新窗口。

装配完成后**再检查一次** `now_ns() >= deadline_ns`：完整帧若在窗口关闭后才到齐，返回 `partial_frame` 而非 `released`。这正是计划要求的“OS 调度晚返回”与“把晚到释放认定为有效”两类事实分开记录。

`Gate` 提供可注入的 `Clock`，测试可用虚拟时钟精确覆盖“截止前 / 等号 / 之后”。

### 2.3 停止接口改为谓词（§3.2）

`wait()` 的签名从 `wait(const bool *)` 改为 `wait(const StopPredicate &)`，`StopPredicate = std::function<bool()>`。

原因如计划所述：`std::atomic<bool>*` 不能合法转成 `const bool*`，复制成局部 bool 只得到一次快照。谓词让调用方保留内存序，gate 只负责调用：

```cpp
gate.wait([&] {
  return stopping.load(std::memory_order_relaxed)
      || fatal_.load(std::memory_order_relaxed);
});
```

同时补上**读取后再次检查**：旧实现只在每次 read 前查 stop，若 stop 在 read 期间置位而该 read 返回完整帧，循环直接结束，结果是 `released`。58 号在同一线程内复现了这个缺陷。现在装配完成后再查一次，stop 优先于帧。

### 2.4 等待分片化

每次 read 最多等 50 ms（`kSliceNs`），因此即使 Driver 从不写入，谓词也能在 50 ms 内被观察到。这与 Worker 现有 500 ms 关闭 grace 相容；计划指出的“2 s gate 等待可能跨过关闭 grace”不再成立。

## 4. 审计补强

派生副本：`implementation/audit_v4/`。57 包审计原件未改。

### 4.1 完整配置的基准改为已固定合同（§3.3）

v3 把 `manifests['worker']['contract_configuration']` 当作基准传入 `check_role_identity`。三个角色只要声明同一个错误配置就能互相“证明一致”。

现在基准是 `c`——从 registry 按 hash 固定的合同文件读出的 typed 配置。合同文件本身就是 84 个字段的 typed 配置，无需新格式。

### 4.2 Driver 工具 SHA 用正确字段名（§3.4）

v3 检查 `if 'driver_tool_sha256' in dm`，但实际 manifest 从没写过这个键（真实字段是 `tool_sha256`），所以整段比较被静默跳过。现在改为**要求该字段存在**并显式比较。

### 4.3 变异比较改为同层次（§5.2）

v3 的 `assert mutated != ctx` 把子对象与整个 context 比较，任何子对象都天然不同于外层 dict，因此这个断言恒真。

现在 `prepare()` 返回 `(mutated, original)` 二元组，`must_reject` 在同一层次比较。`original` 在变异前于同一函数内复制，确保比较的确实是同一个对象。

## 5. 非 ROS exec FD 验证（§7.2）

入口：`implementation/w2_fd_exec/fd_exec_verification.py`。

这一步验证的是**真实 execve 之后**的继承关系，进程内 pipe 测试做不到。全部 9 项通过：

| 检查 | 结果 |
| --- | --- |
| Worker 继承的是读端 | ✓ |
| Worker 只持有该通道一次（无写端副本） | ✓ |
| 读端不可写 | ✓ |
| 兄弟角色不持有任何 release 通道 pipe | ✓ |
| 父进程写端未关时无 EOF | ✓ |
| 父进程写入的 44 字节帧完整到达 | ✓ |
| 关闭写端后读端返回 EOF | ✓ |
| 向读端写入被拒绝 | ✓ |

比较用 **pipe inode 身份**而非 fd 号：fd 号是每进程的，父进程的 3 和子进程的 3 是没有关系的槽位。stdio（0/1/2）被排除，因为 subprocess 会给子进程自己的 stdout/stderr 管道。

### 5.1 这直接推翻了 57 包的接线错误

57 号 W2 步骤 1 文档写的 `pass_fds=(write_fd,)` 是反的。正确关系是 Worker 只继承**读端**、Driver 保留**写端**。本次验证按正确方向实施并全部通过，57 包文档已在本次交付中标注更正。

## 7. 边界

- 本次**没有**做 §7.1 的作者树派生、§7.3 的内部 hook 接线、以及任何 W2 owned 运行。进程是否真的停在 `BeforeCall` 边界、跨多拍后过期分支的终局，仍未验证。
- FD 验证用的是 Python 子进程，不是编译后的 Worker ELF；`pass_fds` 语义相同，但实际 Worker 的 manifest 登记仍需在接线时补。
- 组件与 pipe 测试仍不覆盖跨 exec 的真实 Worker 读取。
- `kDuplicateRelease` 枚举目前仍没有实际返回路径（计划 §5.2 指出）；gate 用 `done_` 保证只消费一次，但“检测并报告重复释放”尚未实现——本次未改这一点，保持登记为已知边界。
- 完整 M4、F6、P1、plant 接受、硬实时与研究结论保持 false。
