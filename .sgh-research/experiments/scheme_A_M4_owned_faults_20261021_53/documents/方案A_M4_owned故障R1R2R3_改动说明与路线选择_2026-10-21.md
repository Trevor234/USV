## 2. 为什么要这么改

### 2.1 目标：补 M4 九组义务表里的 `publication_exit`

九组中 `publication_exit` 的第 2 条 required case 是：

> `worker death, active watchdog, capability lease and cleanup failed`

52 批的状态是：只有 50 批的 16 个 **return-seam 注入**组件，`new_full_owned_fault_runs=0`。
也就是说，**从未有过一次真实的四角色故障运行**。R1/R2/R3 就是补这个。

### 2.2 为什么刺激只能来自外部进程信号

两个硬约束，缺一不可：

1. 冻结合同 `p1_full_contract.hpp:95`：`contract_require(c.at("fault_injection_enabled")==false, "formal fault injection prohibited")`。
2. Regulator 在 `regulator_owned_execute.cpp:99-100` 显式拒绝任何带故障钩子的 Worker：
   ```cpp
   require(... wm.at("fault_injection_permission")==false &&
     wm.at("runtime_hook_values").at("test_delay_ms")==0 &&
     wm.at("runtime_hook_values").at("test_native_block_ms")==0 &&
     wm.at("diagnostic_v2").at("policy")=="none", "M4 exact nonfault Worker");
   ```

所以不能改 Worker 源码注入延迟/阻塞，也不能把外部 kill 描述成"Worker 自身启用了诊断钩子"。

### 2.3 三个 case 各自在验证什么

| case | 边界（触发点） | 刺激 | 要证明的机制 |
| --- | --- | --- | --- |
| **R1** | ready.json 已写、grant.json 不存在 | SIGINT → Regulator | 授权前的取消路径不产生任何物理 API |
| **R2** | 首个 `accepted` 且 `returned=[true,true]` 的 API pair | SIGKILL → Worker | 真实进程死亡 → 失活转移 → 停止新提交/激活 → 有界 ramp |
| **R3** | 同 R2 | **SIGSTOP** → Worker | capability 接收租约过期（与进程死亡无关的独立失败路径） |

### 2.4 为什么 R3 必须用 SIGSTOP

这是本批最有价值的技术点。要证明"租约过期"而不是"进程死了"，必须让 Worker **活着但不发心跳**。

| 事实 | 位置 | 含义 |
| --- | --- | --- |
| `pidfd` 的 `POLLIN` 只在进程**退出**时触发 | `p1_worker_liveness.hpp:25-30` | SIGSTOP 不会让 `WorkerLiveness` 报死亡 |
| Worker 每 200 ms 发一次 capability | `solver_worker_m4.cpp:58` | 冻结后心跳停止 |
| 租约 600 ms | 冻结合同 | 3 个周期后过期 |
| `unusable_locked()` 幂等（`if(worker_unusable_)return;`） | `regulator_owned_execute.cpp:495` | 一旦置位，后续分支不再执行 |
| 租约检查在 `check_worker_locked()` 内先于 watchdog | `:507` vs `:1017` | **lease 必然先触发** |

因此 R3 观测到的必然是租约，不可能是 1 s 的 active watchdog。实测 775.5 ms 正好落在 600–1000 ms 的独占区间，原因码 `worker_capability_expired`。

### 2.5 为什么必须重建全部 6 个 target（而不是 3 个角色）

| 事实 | 位置 |
| --- | --- |
| `P1_DRIVER_TOOL_SHA256` 只有一个消费者 | `formal_owned_runtime.hpp:140` |
| Driver `.py` 在 source bundle 内（82 文件之一） | `build_runtime_v1.py:29-31` |
| 两个宏经 `link_owned()` 编入**全部** 6 个 target | `author/CMakeLists.txt:22-27` |

改动 Driver 会同时改变 driver SHA 与 bundle SHA，两者都被编译进每个 target。所以"只重建 3 个角色"是错的。

## 5. 三条路：优点与缺点

### 路线 1：派生「故障能力 Worker」变体

**能闭合**：`native_block_and_delivery`（native 阻塞 + 结果延迟/丢失）、`active watchdog`。

**做法**：新建一份 `p1_execution_contract_vN.json`，把 `fault_injection_enabled` 置 true，派生一个只在该合同下才接受故障钩子的 Worker 与 Regulator 变体（保留原冻结合同不变）。

| 优点 | 缺点 |
| --- | --- |
| 唯一能覆盖 native 阻塞与 watchdog 的路径 | **与"冻结合同禁止故障注入"这一原则直接冲突**，必须新开合同版本并在文档里严格区分 |
| Worker 已有现成钩子（`test_delay_ms` / `test_native_block_ms` / `diagnostic_v2`） | 需要改 Regulator 的拒绝断言 → **C++ 改动**，打破本批"零 C++ 改动"的性质 |
| 可复用 49 的验证基础设施 | 新合同变体意味着 6 个 target 再全部重建、三层 SHA 链重新建立 |
| | 有"为了让测试通过而放宽门禁"的观感风险，必须在报告里说清边界 |
| | 估计工作量：**中到高**（合同 + Worker + Regulator + 构建 + 验证 + 审计） |

### 路线 2：派生「可注入 Fixture」变体

**能闭合**：`state_clock`（pause/reset/jump/RTF/mixed skew）、`task_reference`（clear/替换/重发/失配）、
`compatibility_input`（独立 fixture）、`candidate_identity_shape`（部分，取决于能否注入指定 GID）。

**做法**：新 Fixture 变体，支持参数化的时钟跳变、path/profile 替换、以及受控的损坏输入。

| 优点 | 缺点 |
| --- | --- |
| 一次改动覆盖**最多**的义务组（4–5 组） | Fixture 当前硬性要求 `mode=="C" && reference_speed==0.05`（`synthetic_source_m4.cpp:34`），放宽它会改变"名义域"的定义 |
| 仍是"外部注入"语义，不违反合同 | `owned_input()` 只接受 Fixture GID，伪造候选仍需真实 Worker 发布端 |
| Fixture 不是安全内核，改动风险低于改 Regulator | 新 Fixture 会改变 bundle 与所有角色身份，需全链重建 |
| | `candidate_identity_shape` 仍需 Worker 侧配合 |
| | 工作量：**高**（Fixture 是最大的一块，且要设计参数化故障谱） |

### 路线 3：登记剩余六组为「需新合同版本」，转入 F6 已知模型事务（**推荐**）

**做法**：把六组写成一份 explicit 的「未闭合 + 阻断理由 + 所需前置」清单，封存本批；
下一批直接做 F6：两个有限数值模型（M0/M1）的 model+plan 原子提交、固定 tick 激活、旧/mixed 候选拒绝、warm-start 分离。

| 优点 | 缺点 |
| --- | --- |
| **F6 是研究方案 A 的核心维度**：「在线残差模型切换」目前在代码里是 0；M4 九组只是执行链完备性 | 完整 M4 阶段仍不合格，答辩时"为何跳过"需要解释 |
| `Version::model` / `Version::config` 从不自增（这是研究核心维度的空转门），F6 正是修它的地方 | 剩余六组将来仍需补，债会累积 |
| 剩余六组对论文贡献的边际价值低于 F6 | 需要向导师/评委说明优先级判断的依据 |
| 工作量：**中**（30 批已有有限模型事务设计稿，可复用） | |
| 不引入新合同变体，不破坏"零 C++ 改动"的既有证据链 | |

## 6. 我的建议与理由

**建议走路线 3，但在转入 F6 之前先做 §4.2 的台架复现。**

理由按重要性排序：

1. **五批（49–53）都在补执行链的完备性，研究问题的核心维度（模型切换）仍是零代码。**
   项目自己的交接文档 §6 就写着："继续增加组件测试数本身不会增加论文贡献。"
   现在正是那句话生效的时刻。
2. **`Version::model` / `Version::config` 从不自增**——这意味着"M4 模型身份门"比较的是一个常量，
   而**它恰恰是研究方案 A 存在的理由**。F6 会强制把这个门变成真的。
3. **剩余六组里有两组是本批亲手证明不可外部隔离的**（active watchdog 已写进 `W1_watchdog_not_isolable_v1.json`），
   这本身就是"外部信号路线已到边界"的证据，不是消极回避。
4. **路线 1 和 2 都要求改 C++**，会打破 49–53 五批积累的"控制内核逐字节未变"这一最有力的证据性质。
   如果将来要改，也应作为**显式的新版本**，而不是混进故障包。

**如果你更看重 M4 整组闭合**（例如答辩要求"九组全绿"），那么路线 2 的性价比高于路线 1——它一次能覆盖 4–5 组，
且 Fixture 不是安全内核。但要有心理准备：这会是一个比 53 批大得多的工程。
