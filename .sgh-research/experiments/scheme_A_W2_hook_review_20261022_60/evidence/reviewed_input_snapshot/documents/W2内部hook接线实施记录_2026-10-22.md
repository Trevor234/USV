## 2. 接线结构

### 2.1 为什么在 `BeforeCall` 内部边界

现有 `owned_cold::Backend::invoke` 的顺序是：内部 deadline 检查 → hook → 实际 `solver_.step`。59 号计划 §4.2/§5.4 明确要求把等待放在这里，而不是 Worker 外层 guard 之前——外层检查发生在进入等待之前，无法作为释放后的最后 guard。

实施后 `invoke` 的顺序为：

1. `clock_() <= deadline`（原有内部检查）
2. **W2 boundary**：`matches()` 判断是否本边界 → `enter()` 等待释放 → 最后 guard 判 stop 与 deadline
3. 通过后才 `mark_native_entered()` 并调用 `solver_.step`

### 2.2 两道期限分别管理（§5.1）

| 期限 | 字段 | 决定什么 |
| --- | --- | --- |
| gate 等待窗口 | `wait_budget_ns` | 释放帧是否在登记窗口内到达 |
| Job 绝对截止 | `job_deadline_ns` | 释放后能否进入实际 C 调用 |

`BoundaryRecord` 分别记录 `released_ns`、`guard_ns`、`job_deadline_ns`、`past_deadline_ns`。`disposition` 把两者组合成五个互不相同的终局：

- `not_armed` —— 未登记 gate，原路径
- `allowed` —— 释放验证通过且仍在截止内
- `expired` —— **释放验证通过但截止已过**（长等待 case 的预期终局）
- `stopped` —— 停止
- `wait_failed` —— 等待窗口内没拿到合法释放

跨多拍时 `expired` 是正确结果，不是失败：计划 §5.1 明确“不要求该 Job 再正常求解”。

### 2.3 调用事实不被偷换（§5.4）

`actual_native_invoked` 只在 `mark_native_entered()` 里置位，而该方法在 guard 通过之后、`solver_.step` 之前调用。外层 `solver_invoked`、进入 C++ 包装器、gate 返回 `released` 三者都不会写这个字段。

测试 `NativeEntryIsRecordedOnlyWhenMarked` 与变异 `mark_call_before_guard` 锁定这一点。

### 2.4 FD 方向（§4.1 / 58 号更正）

Driver：`w2_channel_open()` 建 pipe → Worker 的 `spawn(..., pass_fds=(read_fd,))` → **spawn 后立即 `os.close(read_fd)`**，父进程只留写端。

Worker：`arm_w2_boundary_()` 校验 `/proc/self/fd/N` 解析为 `pipe:[...]`、`fstat` 确认 `O_RDONLY`，并拒绝没有诊断 profile 的启用。

### 3.2 变异（5 个全部被捕获）

| 变异 | 被谁捕获 |
| --- | --- |
| 删除过期 guard | `ReleasedButPastTheJobDeadlineIsExpiredNotAllowed` 等 3 项 |
| 过期判据改 `>=` | `ReleaseAtExactlyTheDeadlineIsAllowed` |
| 只按 ordinal 绑定 | `AnotherJobWithTheSameOrdinalIsNotHeld`、`UnmatchedCallIsNotTreatedAsARejection` |
| 提前置调用事实 | `NativeEntryIsRecordedOnlyWhenMarked` 等 |
| Backend 不查 `matches` | `UnmatchedCallIsNotTreatedAsARejection` |

### 3.3 变异测试抓到的真实缺陷

**Backend 把非注册调用当成拒绝。** 初版 `invoke` 里写的是 `if (boundary_ && boundary_->enter(...))`，而 `enter()` 对非注册调用返回 **false**（它没有等待，也没有记录），于是每个不匹配的调用都会被抛成 `w2_boundary_not_armed`。接线到 Worker 后，一个只在 Job 2/ordinal 1 上等待的 gate 会让 Job 1 的全部调用失败。

修法是在 backend 侧先问 `matches()`，只有匹配的调用才进入 gate。这个缺陷**只会在接线后出现**——单独的 boundary 测试发现不了，因为它测的是 boundary 自身的行为；`backend_rejects_unmatched_calls` 这个变异正是为它写的。

### 3.4 一个不可达的纵深防御

boundary 里在 `gate_->wait()` 返回后再检查一次 `stop_at_release`。这条路径在当前 v2 Gate 下**不可达**：Gate 自己会在装配完成后重新检查谓词并返回 `stop_requested`，boundary 永远看不到一个带 stop 的 `released`。

我把这个变异的断言如实移除了，而不是伪造一个能覆盖它的测试。文档与报告都记录为“不可达的纵深防御”，不称为已覆盖。
