# 第28批最小计划：因果激活状态选择与有界原子重验

第27批组件完成、实际实验 NoGo。接下来优先解除实际激活链路的两个结构性障碍；保留第27批全部冻结源码、预注册、两次初始构建失败与原 NoGo 证据，创建独立新作者目录和新诊断修订。固定以下顺序。

## 1. 先完成只读因果可行性审查

以第27批全部实际候选激活快照和对应的真实已接收输入为样本，先界定“捕获时已经收到、版本相容、时间不晚于冻结目标”的状态选择规则。第27批已证明七个负时间区间都有较早 Odom 可用；尚需证明候选状态的完整有效性。

必须同时审查 Odom 与必要 IMU 的来源、接收时刻、有效代数、源时效、帧和混合条件；不把目标之后才到达的样本当成因果输入。完整验证原 held/publication history 在所选状态时刻已有双通道覆盖，并只向冻结目标前向传播。历史点不能改写为最新回调时间，不能把负区间夹为零，不能反向积分。

离线结果只决定是否具备实施依据，不回写第27批决策，也不宣称“如果重跑就能全过”。如果出现缺失历史、混合条件不清或原时效门不满足，保留拒绝并收敛方案，不进入闭环实验。

## 2. 实现有界状态快照，并保留原提交检查

在新诊断修订中，明确规定历史输入容量、每次选择上界、纪元/配置/模型/任务失效时的清除策略；历史记录由本次已认证回调提交产生。选取最近且不晚于冻结目标、满足完整原输入域的状态或状态组合。容量与工作量必须预先固定，不引入无界搜索、等待传感器或后台无限重算。

对“锁外验证期间输入变化”，保留原版本、Odom 序列、IMU 序列比较。最多增加一次完整的重新捕获与验证；同一个 Ticket/Candidate 只被消费一次，最终激活、adapter inspect、Decision 和发布各执行一次。若重验仍变化、时间不足、版本变化或任何旧门失败，沿原拒绝/零回退流程处理。不能重新求解或重新武装已消费的冷启动策略。

两个机制需要分清：历史状态选择解决目标早于最新 Odom；重新捕获解决验证期间回调竞争。仅重试最新快照可能仍得到更晚 Odom，不能替代历史选择。

## 3. 同步严格合同、观测和诊断记录域

Worker 与 Observer 的精确合同、资源修订及规范同时推进新诊断修订。未明确变更的模型、代价、N/dt、输入/速率/时效/源未来限制、150 ms 截止、200 ms 周期、20 ms 抖动和目标模拟时间误差、原 RMSE 门全部保持。

在激活证据中记录所选历史输入的完整来源、序列/代数/时刻、捕获水位、前向区间、尝试次数和每次拒绝原因，以便独立检查器重建真实选择和最终提交。修改规则与观测同时入冻结源码，不事后补成功证据。

单独修复 `reference_pair_retry` 启动缺口：只有合法触发已经提交、对侧在当时确实不存在、没有冻结、仍在等待，才允许对侧序列为零及其原缺省时刻。保留正常正序列的原检查，新增伪造零序列、缺失对侧却冻结、有对侧提交却声明不存在等负例。不要改写第27批报告。

## 4. 在任何新五角色运行前完成必要组件验证

有限验证应使用真实生产选择/提交路径，并区分构造前提和实际观测：

| 场景 | 必须观察到的行为 |
|---|---|
| 第27批七个负区间的实际输入前缀 | 可选历史点满足因果性与原输入域，完整前向重建；不使用未来样本。 |
| 没有合格历史点、缺一路输入历史、源/接收过期、纪元或版本变化 | 保留拒绝。 |
| IMU 先到/后到及混合条件变化 | 完整规则重验，不能用删掉原 IMU 序列比较来过测试。 |
| 首次验证期间恰好一次回调变化 | 最多一次重捕获，原门全部重新执行；同一候选只提交一次。 |
| 第二次仍变化、达到原时间边界或关闭期间变化 | 有界退出、拒绝，无额外发布。 |
| 冷启动已消费、候选之前被拒绝、之后有新任务代数 | 不再执行冷启动四次策略，后续自由求解语义不变。 |
| 正常回归与原拒绝/关闭反例 | 所有现有原生目标继续通过，保留父级冻结反例与全部失败构建。 |

先检查真实包含路径、严格资源修订与编译依赖，避免重复第27批初始构建中的两个接线错误。成功构建需要冻结源码与实际链接库、嵌入源码 pin、原生测试结果及有效合同一致。

## 5. 最后才执行一次原首档

重新做 S0 本地资产与工作区核验；S1 以新进程、新通信身份、新二进制和运行时不可变配置检查认证有效入口。新 Go/NoGo 仅授权一次受控 localhost 首档，不能继承旧端点资格。

预注册仍为 0.05 m/s、Ready 至实际驱动关闭请求的完整 20 s；所有候选接受、至少连续 90 次和 18 s 覆盖、全窗 RMSE ≤0.007392495755251466 m/s、最后 5 s 平均速度误差 ≤5%。额外必须联结首 Job 的四次原生求解 → Candidate `[0.5,0.5]` → 实际接受 Decision → Publisher 双通道返回 → 成功 StoredApplied。任一环不满足即 NoGo。

全窗首档通过后，才能讨论其性能与下一速度。若首控未实际施加，继续定位激活或发布链；若施加且激活门通过但 RMSE 失败，再研究控制性能。每批均分列组件验证、实验资格、研究结论及本地/远端归档状态。第24–27批 MPC 待交付列表继续保留，只有完整复制与回读成功才登记交付。
