# 模型事务后续接口约束与接线次序

本文件是127批的评审设计。运行时热切换、Worker迁移、消息或合同扩展均未实施。当前代码草案仅提取packing及初始化setter检查，仍只有构造期初始化入口。

## 1. 本次固定的基础层边界

`p_global_pack.hpp`只把MpcParams映射为30个double，不改变值、不验证物理模型。`p_global_apply.hpp`在调用前检查空capsule、空函数指针和非有限参数，用私有240字节副本调用同步setter，并返回实际报告的状态。

它不负责注册模型、选择generation、reset warm、提交Job、创建/销毁capsule或改变线程所有权。异常交由拥有者处理；不能把函数返回0称为整个模型事务已成功，也不能据此发布新的model_generation。

固定布局：

| 索引 | 内容 |
|---|---|
| 0—3 | mass、Iz、xg、d_thruster |
| 4—8 | Xu_dot、Yv_dot、Yr_dot、Nv_dot、Nr_dot |
| 9—13 | Xu、Yv、Yr、Nv、Nr |
| 14—18 | Xuu、Yvv、Yrr、Nvv、Nrr |
| 19—24 | Q的6维 |
| 25—26 | R的2维 |
| 27—28 | Rd的2维 |
| 29 | Qf_scale |

尺寸、目标函数、默认权重、动力学数值、参考几何与codegen结构保持；测试数据里的独立索引哨兵只用于检查布局。

## 2. 三项必须显式处理的接线问题

### 2.1 现有Worker的创建、使用和销毁线程不同

126主谱系`worker/solver_worker_m4.cpp`在Node构造中创建`solver_`，在`work()`线程使用；Node最终在主线程销毁成员。`capability()`还直接读取`solver_->backend()/N()/dt()`。126实验事务层却规定构造线程为唯一所有者，运行时方法和可变状态查询会拒绝其他线程。

所以不得将实验类替换该成员后宣称接通。下一段接线设计应固定为：求解线程创建、使用、销毁capsule；main/capability读取独立的不可变backend/N/dt描述，不访问活capsule。初始化成功通过明确ready状态交给启动协议，不能为了迁移而让尚未初始化的对象提前获得正常执行准入。

启动顺序需沿现有recording-ready链复核，避免“求解线程等图收敛、图收敛又等solver ready”的循环。失败应保留具名Source及fatal终局；不重启、不将创建失败伪装成有心跳即有求解能力。

### 2.2 model_generation是完整reference binding的一部分

当前ScopedEpoch的Binding包括task/model/config/schedule/clock epoch及run、boot、合同、nominal和path/profile指纹。模型版本变化会改变binding。普通不可变terminal策略和已登记scoped策略的后果不同，不能仅改Job.model_generation而保留“旧参考可继续使用”的假设。

运行时接线前必须登记：谁提交模型激活意图、哪一拍使Regulator版本生效、旧候选/参考如何失效、是否允许开启新窗口，以及回切旧模型时如何形成合法新binding。不得为绕过ledger而忽略旧绑定或临时借用一个未定义计数器。

现阶段次序仍为共享基础层先、Epoch政策评审后；模型热切换的组合接线须在两项接口一致后单独登记。有限F6回切正例不能代替这个跨进程版本协议。

### 2.3 生成setter没有传播内部precompute返回值

当前生成C函数检查长度不匹配时调用exit，执行`fun->casadi_fun(...)`后固定返回0。包装层可以拒绝非有限输入、约束长度并消费报告的非零返回；它不能据此证明所有内部precompute故障都被观测。

本批不改生成C。后续选择更强错误传播或故障隔离时须有单独接口/生成路径评审与实际反例。adapter或链接边界返回17只验证C++调用者对错误结果的策略，不能称为native C内部故障覆盖。

## 3. 运行时请求的推荐最小合同

补充一项生产落位前条件：当前`mpc_solver.cpp`的工厂会捕获AcadosBackend构造异常，并在编译支持时尝试CasADi。checked初始化新增的异常可能触发后端切换。直接Backend对拍已验证新增拒绝与清理，但没有验证实际CasADi数值后端或工厂的性能/诊断链；不能将“构造拒绝”直接称为“整机停止”。实际工厂的两种构建模式及后端选择、诊断和deadline行为须在落位前单独验证。

此外，实际owned链为`owned_cold::Backend -> startup_replay::RawBackend`。126的`raw_backend_v1.hpp`仍直接拼装30维数组并调用setter。本批复用的是生产Backend草案与独立F6实验层；实际Worker RawBackend尚未迁移，不能据此声称所有调用者已统一。

先采用启动时固定的有限模型表，每个model_generation绑定唯一参数内容和摘要；不在本段引入GP训练、动态下载、第二套DDS总线或无界模型注册。未登记模型不能进准备路径。

优先复用现有有界Job提交槽，由Job选择已登记模型，避免同时增加另一个无明确排序的模型命令队列。Regulator的激活计划、Worker选择规则和reference版本变更必须共同事前登记；本建议未写入运行角色。

| 边界 | 后续接线必须满足的条件 |
|---|---|
| 接收 | run/boot/合同/版本表与完整Job身份匹配；有限参数及参考形状成立 |
| 排队 | 现有pending Job槽保持有界；替换、过期、关闭逐Job记账 |
| prepare | 唯一求解线程检查目标版本、当前状态、停止和原绝对截止；不持Source/capability所需锁 |
| native修改 | setter、必要reset及规定检查完成后才能发布当前模型身份；耗时计入原Job总预算 |
| commit后过期 | 即使模型已成功应用，已过期Job仍不得进入C solve，不续deadline、不改solve/kernel时间字段掩盖准备耗时 |
| 未触碰capsule的取消 | 可恢复原UNCOMMITTED/READY |
| 已触碰后的不确定失败 | FAULTED并隔离，不能abort假回滚；每个pending Job有终局 |
| 关闭 | 求解线程完成其胶囊销毁；Source与capability按原关闭合同独立记账 |

`nominal_hash`表示基线plant还是当前controller模型、模型表摘要怎样绑定注册、参考内容怎样与模型版本配对，都须在正式合同中明确。不能在编码时自行解释。

## 4. 固定实施顺序与验收

1. 独立审查纯packing补丁。要求当前源码同编译配方的默认路径、warm、已下发锚、reset、分级fallback、fail_count、N/dt及权重门均保持；30槽位逐bit正确。
2. 单独审查checked初始化补丁。正常域保持；报告错误和非有限hydro的新增拒绝是明确行为变化，必须验证清理与C solve为0，不伪称所有错误路径都与旧版本相同。
3. 将共同头用于实验事务层，有限M0/M1及状态机仍通过；不得顺手复制实验solve实现进生产。
4. 完成Worker所有者/不可变capability描述与启动协议设计，补实际创建/使用/销毁和关闭交错反例。
5. 完成model/reference绑定及激活tick合同，再做Epoch政策与模型接线组合评审；旧策略关闭负控、能力开启正控分别登记。
6. 只有前述接口闭合后才生成新freeze/registry/registration，决定一条有限owned是否必要。新owned自动重试0；历史失败保留；阶段资格不自动晋级。

当前评审能放行的范围最多是有实测支撑的基础层草案；运行时热更新和P1仍有明确未闭合接口。
