## 2. 关键设计点

**E3 的顺序很重要。** guard 现在是：

```cpp
if(stop_&&stop_())return false;
if(clock_()>current_deadline_ns_)return false;
if(!boundary_->armed()||!boundary_->matches(ordinal,current_job_))return true;
return boundary_->permit_native_entry(stop_);
```

前两行对所有内部调用生效（包括非目标 Job 和恢复的 BeforeCall 路径）；`matches` 只决定是否多做一次 gate 语义检查。这样"非目标调用免 gate，不免原有执行约束"。

**E4 用两个出口保一致。** 拒绝路径在 Backend catch 里重刷 policy；正常路径在调用后刷新。`actual_native_invoked` 只由 C 入口的观察者置位，异常不把它改回 false。

**E5 需要源码级检查。** 编译型单元测试验证的是 helper 本身，看不到"Worker 是否真的合并了 helper 集合"。`run_source_contract.py` 直接读生产源码断言 10 条组合关系，并接入 runner 的变异判定。

## 4. 过程中我自己修掉的三个工具缺陷

1. **`terminal_catch_clears_active` 检查过宽**：最初用固定长度窗口，`active_=0;` 在正常完成路径上也有，变异后仍 PASS。改为锚定 catch 自身的 `break;}` 边界。
2. **catch 锚点抓错**：文件里有多个 `catch(const std::exception & e)`，第一版 `index` 命中了 `wait_recording_ready` 的那个。改用从 `terminal_exception` 反向 `rindex`。
3. **`worker_whitelist_skips_helper` 未被捕获**：它破坏的是 Python 侧组合关系，C++ suite 看不到。加了 `COMPOSITION_MUTATIONS` 映射，让 runner 对该变异跑源码检查。

这三个都不是产品缺陷，但都是"验证器本身可能假装通过"的实例，和这轮审查反复强调的问题同类。
