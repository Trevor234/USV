# Isolated F5 publisher startup/release implementation

This directory derives `mpc_node.cpp`, `mpc_node.hpp`, and `research_logger.hpp` from the exact frozen F5 bytes in `../../m0b_D1_chain_20261009/reference_detail/verified_sources`. The original files are preserved. `src/mpc_node_main.cpp` is an exact copy of the separately verified frozen original, preserving its three-thread executor and pre-shutdown lifecycle callback. No code was deployed to the ROS workspace, no tests were executed by the implementation agent, and no Gazebo or D1 collection was started.

The new binary has a mandatory held output state. Its constructor requires research logging, reference prediction logging, VRX output, and the original F5 baseline lineage. It obtains the producer from the newly allocated `ResearchLogger`, then writes `startup_manifest.json` before creating the control timer. The manifest records the exact run, producer, config, nominal hash, boot/domain, executing binary hash, process start ticks, immutable compile-time source bundle hash, original F5 manifest hash, and original node source hash. The manifest's self-reported process fields are inputs for independent driver authentication and are not themselves that authentication.

The timer reads a mandatory absolute `p1_release_file`, using component-by-component no-symlink directory opens and a bounded single-link regular file read. The release envelope has exact keys, rejects duplicate JSON keys, and requires the exact run, producer, startup manifest hash, a 32-character lowercase hexadecimal nonce, a driver evidence SHA256, an integer `valid_until_steady_ns`, and three explicit boolean attestations: subscriptions verified, effective external Worker hooks zero, and one owner for both physical channels. Initial acceptance must occur before the deadline, which must be within 60 seconds of validation. The gate checks expiry again after arming and after receipt I/O. The expiry limits initial acceptance and does not revoke an already accepted release. These attestations must be independently proven by the driver; the publisher records that it does not independently prove them. Graph names and endpoint GIDs alone do not establish an owned process-to-endpoint relation; without independent binding, live release remains unqualified.

Prepared acceptance arms the actual research logger and verifies it is armed before atomically creating a create-only `release_receipt.json`. The receipt explicitly records `status=prepared_acceptance`, `physical_output_state=held_pending_in_memory_commit`, `receipt_qualifies_physical_release=false`, the attempted acceptance time, and the deadline. It records intent before the final in-memory transition, and does not prove that transition or physical release. Only after receipt I/O and the final expiry check succeed does the in-memory gate become released. If receipt I/O has linked a file but fails afterward, or the deadline expires after receipt I/O, any prepared receipt is retained as evidence and output remains held/terminal. Its existence is never described as proof that physical release occurred. Actual first Applied and close/source evidence are needed for that later claim. The manifest and release file remain hash-pinned; mutation or disappearance invalidates output permanently. A second poll of the same valid file is an observation of an already accepted release, and does not arm again or overwrite the receipt. A malformed or unready envelope is terminal for this process instance.

Release acceptance and shutdown share `control_output_mutex_` as their linearization point. The poll holds it through the shutdown check, arm, receipt I/O, expiry check, and in-memory transition; shutdown acquires it before setting its flag. If shutdown acquires it first, no later release can arm or commit and no physical zero is emitted. If release acquires it first, its final transition precedes shutdown's flag and recorded zero. The original final post-solve shutdown check remains in place. Test-only compile-time latches exercise both lock orders inside the actual source paths; production has no latch members, hook calls, or runtime fault parameters.

Every physical entry point, including direct research publication, VRX publication, zero/release helpers, RC helpers, and standby paths, checks the accepted release and logger armed state. The shutdown path never accepts a pending release. Before release it emits no physical zero; after a valid release it retains the original recorded final-zero behavior. Removing or changing an accepted release prevents later physical output, including a shutdown zero. This behavior is a preparation protocol and does not establish a general safe control fallback for a moving vessel. The external lifecycle controller must keep accepted artifacts intact until the publisher has closed and retain observer/recorder through the final Applied/session evidence.

The original numerical reference builder, thrust scaling/clamping formulas, deadline rejection, solver parameters, NMPC model, weights, and solver state updates are untouched. The only control-loop change is the required preparation gate before the original loop. The unrecorded VRX fallback is removed from this derived binary, because release requires telemetry to be armed. The production constructor is never replaced with a test stub; source-linked tests use only the existing private solver friend, extended with `NodeOptions` to supply required startup parameters.

The authored suite contains **43 cases: 32 gate/header cases and 11 actual node cases**. Actual node cases publish only to unique test topics, exercise standby and every output helper while held, verify that the old armed parameter cannot bypass the gate, verify pending release is not accepted during shutdown, observe the first physical pair and Applied sequence 1 with the manifest producer, observe the recorded final-zero/session flush after release, exercise both concurrent release/shutdown lock orders, and demonstrate that expiry after prepared receipt cannot produce a shutdown zero. The counts are authored cases, not passing results. The root agent owns finite preflight, dependency/source verification, compilation, test execution, and postrun evidence.

The standalone CMake requires an explicit verified immutable F5 source package and acados dependency root, never defaulting to live workspace paths. It rebuilds the unchanged core, solver factory/backend, and generated model sources inside the isolated build directory. Optional CasADi capability requires an explicit verified root and the original translation-unit ABI selection. Omitting CasADi must be documented as restricting unused fallback capability; it is not sufficient evidence of full binary equivalence. The root driver must bind the actual selected source/dependency hashes, compile options, binary bytes, and parent lineage before any release.
