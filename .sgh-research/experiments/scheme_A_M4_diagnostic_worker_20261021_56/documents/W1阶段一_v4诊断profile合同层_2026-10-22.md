## 4. 为什么这样设计

### 4.1 不能只把 bool 改成 true

54 号文档 §6.2 明确要求。如果直接放宽 `regulator_owned_execute.cpp:99-100` 的断言，
任何携带 `fault_injection_permission=true` 的 Worker 都会被接受——这会打开一个真实的攻击面。

现在的做法是**两个互斥谓词**：

```cpp
if (m4_owned::diagnostic_profile(c_)) {
  // 只接受精确登记的 1700 ms pre-native stall
  require(... fault_injection_permission==true &&
            test_delay_ms==0 && test_native_block_ms==0 &&
            diagnostic_v2.policy=="pre_native_once_after_completed_v1" &&
            diagnostic_v2.milliseconds==1700 &&
            diagnostic_v2.after_completed_jobs==1 &&
            diagnostic_v2.native_C_hang_claimed==false, ...);
} else {
  // 原有严格拒绝
  require(... fault_injection_permission==false && hooks==0 && policy=="none", ...);
}
```

### 4.2 v4 必须允许 `execute`

`Diagnostic` profile 原本只允许 `no_output`/`shadow`。但 watchdog 判定在 tick 循环里
（`regulator_owned_execute.cpp:1017`），不跑 tick 就永远观察不到 `active_watchdog`。
这是 W1 存在的理由，也是必须新增 profile 而不是复用 `Diagnostic` 的理由。

### 4.3 `execute_qualified=false` 与 `mode=execute` 并存

看起来矛盾，实际上是准确的：
- `execute_qualified` 描述的是**研究资格**（是否达到生产执行标准）→ false
- `mode=execute` 描述的是**运行模式**（Regulator 是否跑 tick 并发布 API）→ 是

隔离诊断 run 需要后者、绝不能声称前者。v4 的断言把这两者分开。

## 6. 一个必须记住的限制

`v2_diagnostic::Block` 的注释和事件都明确写着 `actual_native_invoked=false`。
它在**调用 solver 之前** sleep（`solver_worker_m4.cpp:158/163`），`solve_owned()` 在 `:168`。

因此 W1 得到的是**"计算线程受控驻留"**的证据，**不是**"native C 内部挂起"。
后者需要覆盖真实调用边界的适配实现，属于独立义务（计划中的 W2-native-boundary-hold）。
