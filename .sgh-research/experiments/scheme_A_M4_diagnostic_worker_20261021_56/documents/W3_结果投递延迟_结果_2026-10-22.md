## 1. 结论

`W3-result-delivery-delay` 通过。它证明的是：**候选在 native 求解完成后被人为延迟投递时，
准入层会拒绝它，而不会让整个 run 进入失活。**

这与 W1 形成严格互补：

| | W1-work-stall-watchdog | W3-result-delivery-delay |
| --- | --- | --- |
| 刺激 | pre-native stall 1700 ms | post-native delay 170 ms |
| 心跳 | 继续 | 继续 |
| **必须出现** | `active_watchdog` | **不得出现** watchdog |
| **必须出现** | `worker_unusable_transition` | **不得出现** 失活 |
| 迟到候选 | 不适用 | **≥1 被拒** |
| 结果 | 通过 | 通过 |

## 2. 刺激的精确位置

`test_delay_ms` 作用于 `solver_worker_m4.cpp:175`：

```cpp
result.solve_start_ns = ...;            // :166
result.solver_invoked = true;
answer = solver_->solve_owned(...);     // :168   ← native 求解
result.solve_end_ns = ...;              // :169
...
if(delay_) std::this_thread::sleep_for(...);   // :175  ← 延迟在此
out_->publish(result);                  // :192   ← 候选直到这里才发出
```

**关键**：`solve_start_ns` / `solve_end_ns` **不被重打**。延迟只推迟「候选到达 Regulator」的时刻，
不伪造求解耗时。这正是契约要求的「不得重新打 solve 时间」。

## 4. 首轮暴露的两个真实时序事实

首轮用 260 ms 延迟，实测与预期不同。两项都不是代码缺陷，而是**我对时序的假设错了**：

### 4.1 `wrong_tick` 先于 `late`

`p1_admission.hpp:105-110` 的判定顺序：

```cpp
if(t.target!=current_tick+1)return "wrong_tick";   // :106
if(!(t.version==v))return "version_mismatch";
if(t.deadline!=t.origin+DEADLINE || t.target_ns!=t.origin+T)return "time_contract";
if(now>t.deadline)return "late";                   // :109
```

`wrong_tick` 检查在 `late` **之前**。260 ms 的延迟大于 200 ms 的 tick 周期 T，
候选到达时 `current_tick` 已前进 1–2 拍，所以先命中 `wrong_tick`。

**这是真实行为，不是缺陷**：迟到的候选本来就该被拒，只是拒绝理由取决于它迟到了多少。

### 4.2 观察窗过长导致 `task_time_horizon_exceeds_profile`

首轮 Driver 的观察窗是 60 s，run 实际跑了 62 s。而参考 profile 的时域是有限的
（`task_time_profile_v1.hpp` 的 `static_reference_*` 检查 + Fixture 的 40 s replay 上限）。

结果是 Regulator 报 `task_time_reference:task_time_horizon_exceeds_profile` 并失活——
**与 delay 无关**，纯粹是观察窗太长。

修正：W3 的观察窗缩短到 8 s。

## 5. 修正后的判据

```python
# W3 必须满足
accepted_pairs 可以是 0（run 很短）
late_candidates >= 1              # 确有候选被拒
transition_ns is None             # 不得失活
watchdog_ns is None               # 不得触发 watchdog
ramp_ok is True
四角色 rc 0、group_empty
```

拒绝理由接受 `late` / `wrong_tick` / `cutoff_closed` 三种——它们都是**准入层的合法拒绝**。

**这个判据比原来更准确**：原设计想验证「late 分支」，但实际系统在跨 tick 时会走
`wrong_tick` 分支。把两者都算作合法拒绝，才是对系统行为的忠实描述。
