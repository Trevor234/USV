## 1. 结论

`W4-result-delivery-drop` 通过。它证明：**Worker 完成了 native 求解、生成了 Candidate，
但没有发布它时，Regulator 只看到「没有候选」，并按无候选降级——不会误判为 Worker 死亡。**

这与 53 批 R2 形成本质对照：

| | R2（53 批） | W4（本批） |
| --- | --- | --- |
| Worker 进程 | **死亡（SIGKILL）** | **存活，心跳正常** |
| 求解 | 未完成 | **完成** |
| Candidate | 未生成 | **生成，写入 Source** |
| 投递 | 未投递（进程已死） | **主动丢弃，明确记账** |
| Regulator 反应 | `worker_unusable_transition` | **无失活** |
| decision 原因 | `worker_unusable` | **`no_candidate`** |

**这是"结果投递丢失"与"Worker 死亡"的本质区别。**

---

## 2. 刺激的实现

在 `solver_worker_m4.cpp` 的 candidate 生成与发布之间插入一次性丢弃钩子：

```cpp
generated_candidates_++;
event({{"type","candidate"}, ...});          // :188  完整记录已生成的 Candidate

if(fatal_)break;
if(drop_after_>=0 && generated_candidates_==drop_after_+1){
    event({{"type","diagnostic_candidate_dropped"},
           {"job_id",...}, {"generated_candidates",...},
           {"policy","generate_once_without_publish"},
           {"publish_attempted",false}}, true);   // :191
    continue;                                       // :195  不发布
}
out_->publish(result);                              // 本次不执行
```

**关键设计**：
- 丢弃点在 **Candidate 行写入之后** → Source 能证明"生成过"
- 在 `out_->publish()` **之前** → 不产生 `candidate_publish_result`
- 用 `continue` 而非 `break` → Worker 继续服务后续 job，不进入 terminal

## 5. W4 与 W1 的关键区别

两者都要求"心跳继续"，但结局相反：

| | W1 | W4 |
| --- | --- | --- |
| `active_job` | **持续非零** → 触发 watchdog | 迅速归零 → 不触发 |
| 失活 | **必须有** | **必须没有** |
| 原因 | 计算卡住 | 结果没送到 |

这精确区分了**"计算停滞"与"投递失败"**——两者都是 Worker 侧故障，但需要不同的监督策略。
