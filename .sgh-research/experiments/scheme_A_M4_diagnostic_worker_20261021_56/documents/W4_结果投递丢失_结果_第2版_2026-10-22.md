状态：**通过**（第 1 版报告的因果表述错误，本版更正）

> **本版替代** `W4_结果投递丢失_结果_2026-10-22.md` 的第 1 版。
> 第 1 版把 `no_candidate` 归因于被丢弃的候选，这是**错的**：
> 那次 `no_candidate` 出现在 tick 1，而被丢弃的候选属于 Job 3 / 目标 tick 4。
> 两者相隔三个 tick，因果对不上。第 1 版还漏报了当时 Worker 的
> `active_job` 从未清零——因为跑的是含 `continue` 缺陷的旧二进制。

## 1. 上一版错在哪（必须保留的教训）

| 第 1 版的表述 | 实际情况 |
| --- | --- |
| "那次 `no_candidate` 正是被丢弃的候选本该占据的 tick" | `no_candidate` 在 **tick 1**；被丢候选属于 **Job 3 / target tick 4** |
| "Regulator 正确地按无候选降级" | 降级确实正确，但**不是**这次丢弃造成的；tick 1 的 `no_candidate` 是正常启动期无候选 |
| （未提及）| 旧二进制里 drop 分支用 `continue`，**跳过了 `completed_++` 与 `active_=0`**，capability 连续三次报告 `completed=2 active=3` |
| （未提及）| Driver 在丢弃后**过早退出**，从未观察被丢 Job 的目标 tick 及其后续 tick |

## 2. 修正了什么

### 2.1 Worker：丢弃不再短路收尾

```cpp
const bool result_dropped = drop_after_>=0&&generated_candidates_==uint64_t(drop_after_)+1;
if(result_dropped){
  dropped_candidates_++;
  event({{"type","diagnostic_candidate_dropped"}, ... {"publish_attempted",false}},true);
} else {
  try{out_->publish(result);published_candidates_++;result_published=true;...}
}
}
completed_++;active_=0;                       // 两条路径共用
if(!result.success||!result.prediction_available){
  ... {"result_published",result_published},{"result_dropped",result_dropped} ...
}
```

三个变化：
1. 丢弃**只**跳过 `out_->publish()`，`completed_++`、`active_=0`、数值失败策略全部照常；
2. `terminal_numerical_failure` 的 `result_published` 从硬编码 `true` 改为真实值，并新增 `result_dropped`；
3. 新增 `dropped_candidates_` 计数，`normal_source_complete` 的判据从
   `generated == published` 改为 `generated == published + dropped`——
   否则**按策略丢弃会被误报成 Source 不完整**。

### 2.2 Driver：真正去观察目标 tick

旧 Driver 第 336 行引用了未定义的 `drop_after`。新版：
- 从 Worker 的 `diagnostic_candidate_dropped` 取被丢 `job_id`，再从 Regulator 的 `job` 行反查 `target_tick`；
- 必须在该 tick 看到 `no_candidate` 且未被接受，且该 Job 从未进入 `candidate_registration`；
- 必须看到**至少一个后续业务 tick**且其中有接受（投递恢复）；
- 必须在**没有后续 Job** 的窗口内看到 `active_job=0` 且 `completed_jobs >= 生成数`；
- hold/ramp 的选择由 `hold_ns` **独立复算**，不采信 `control_source` 字段本身。

### 2.3 Fixture：修掉一个真实的单次尝试缺陷

`fixture_start` 刚出现时立即做 DDS 图检查，若发现未收敛就直接终止 run。
现在起跑尝试移到**主循环**（`attempt_start()`），在 2 s 起跑预算内重试；
GID/节点名/唯一发布者三项校验一个字都没放松。

> 第一次的修法（在 timer 回调里阻塞等待）是**错的**：
> `get_publishers_info_by_topic` 的图缓存要靠 executor 服务 graph guard condition 才刷新，
> 在回调里阻塞等于把自己等的那个发现卡死。W1 上立刻就暴露了。
