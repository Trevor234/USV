### 1.2 一个批次包的内部结构

```
scheme_A_<主题>_<日期>_<批号>/
├── CURRENT.md          当前状态（一段话 + 表格，最长不超过 1 页）
├── documents/          主报告（.md，通常 5k–60k 字）
├── postrun/            机器可读回执（step_result / verdict / next_plan / review_findings）
```

这个结构本身是一条纪律：`CURRENT.md` 给人看，`postrun/` 给程序读，`evidence/` 给复核者重算，`implementation/` 保留可重放源码。四者分离，是为了防止「报告写得漂亮但证据对不上」。

## 3. 主线六阶段详解

### 阶段 1｜P0：先把尺子做准（10-03 → 10-16，批 01–19）

**为什么做。** 三处平台缺陷会让后续所有数据失去意义：

1. NMPC 迟到解仍可能进入输出或热启动；
2. v5 ONNX 把归一化动作当物理牛；
3. 录包缺左右推力、最终动作和 clock。

**改了什么。** 三处最小修复 + 五个冻结基线（F1–F5）：

| 项 | 修改 | 作用 | 边界 |
|---|---|---|---|
| 迟到解 | 完整 `solve()` 墙钟耗时与后端耗时共同判定，超预算拒候选、清热启动、恢复发布锚点 | 250/400 ms 阻塞下实测仍发布历史 `[8,12]N` | 同步阻塞期间仍无独立接管（→ P1） |
| ONNX 单位 | 导出图内唯一一次 `25×clip(actor_mean,-1,1)` | 新图实际推力才真正超过原 1 N 上限 | 未证明历史训练资产配套 |
| 录包 | 新增 `/clock`，recorder 保留左右推力/status | 新 bag 三路各 248 条全匹配 | 全部拍完整性未证 |
| F1/F2 | 冻结修复后基线 + StateSnapshot/CycleTiming/AppliedControl 三消息 | 状态、命令、周期时间有明确身份 | 最后一段动作保持仍 `end_unknown` |
| F3 | 同参数三方对拍（Python / C++ / acados 离散函数）+ 四元数门禁 | 291 种不同输入通过；模长平方 < 1e-12 拒 | 同参数相等不证明真船模型准确 |
| F4 | controller/plant 配置分离，记录真实参考与同次返回预测 | 发现实际用的是 profile 参考（中位 0.8 m/s），配置里的 0.6 是 fallback | 质量探针同时改了船体几何，不是纯载荷阶跃 |
| **F5** | **资格复查与输入冻结放进同一把 `state_lock_`** | 关闭「检查通过后输入被 callback 改坏」的竞态 | 不保证候选永久有效 |

**F5 是本阶段最有价值的一处**。旧代码先检查 `can_solve_`，释放锁，再取锁复制输入；两次取锁之间 path callback 可以把合法路径清空或改成单点。改法是在最后一个输入临界区重新检查资格并在同一把锁内冻结 state/reference，锁在 native solve 前释放（不跨求解持有）。

**踩到的坑。** 参考速度口径反复：0.6 m/s 一度被当作实际参考速度，F2 补充勘误、F3 §3、F4 §4 三处一致更正为 profile 速度中位 0.8 m/s。四元数门禁也有一个「同日先后修订」的过程：F2 §7 写「尚未修复」，F3 写「已在 `odom_callback_` 修复」——不是互斥矛盾，是同日两次报告。

**阶段判定。** P0 整阶段**部分完成**：plant/controller 参数独立、训练端历史时序、plant 接受/精确执行时序、GP 标签合同均未闭合。

| R2 | 首个 accepted 且 returned=[true,true] 的 API pair | SIGKILL → Worker | `worker_process_exited` | 刺激→转移 **175.7 ms**；后续 6 个 fallback pair；新 job/candidate 0/0；Worker rc −9 |
| R3 | 同 R2 | **SIGSTOP** → Worker | `worker_capability_expired` | 刺激→转移 **775.5 ms** |

R3 是这批最有技术含量的一处。要证明「租约过期」而非「进程死了」，必须让 Worker **活着但不发心跳**：

- `pidfd` 的 `POLLIN` 只在进程**退出**时触发（`p1_worker_liveness.hpp:25-30`）→ SIGSTOP 不会让 liveness 报死亡；
- Worker 每 200 ms 发一次 capability（`solver_worker_m4.cpp:58`）→ 冻结后心跳停止；
- 租约 600 ms → 三个周期后过期；
- 租约检查在 `check_worker_locked()` 内**先于** 1 s watchdog（`:507` vs `:1017`）。

所以 775.5 ms 必然落在 600–1000 ms 的独占区间，原因码 `worker_capability_expired`。

**53 批自己做出的关键判断**：`active watchdog` **结构性不可外部隔离**（W1 记录在案）。这直接决定了后续必须走「派生诊断版本」而不是继续发信号——就是 56–57 批的 W1/W3/W4 隔离诊断。

### 阶段 5｜F6：研究核心维度第一次有代码（10-25，批 102–110）

**两件事同时发生。**

#### 5.1 scoped Epoch（102–105）

**问题**：原 Epoch 按静态任务设计，绑定一旦变化就进入终态。持续运行场景下，这会永久阻止后续 Job 提交。94 批曾把它误归因为「5 s drain 时间不足」，111 批用同一 run 的事件流证明真因是单代终态（`epoch_terminal@tick3`）。

**解法**：包装层，**原 Epoch 类零改动**（冻结头字节不变，freeze 内有断言）。旧代确已终态 → 同锁 quiesce → 退役进有界 ledger → 用新 binding 建新 Epoch 实例。新 Job 继续使用全 run 递增的 job_id。

六个守卫（G1–G6）：

1. 旧代确已终态在册
2. 同锁 quiesce
3. 完整绑定不能重复
4. 静态参考域不放宽
5. Job 跨代单调
6. 代数/账本有界（默认 8 代）

**实测（104 批）**：同 run `generation 1→2`、`task_generation 2→6`、Job 1–27 继续、存在新代接受；NEG 无换届事件。**这是真实的进展**——从「换参考后一直 epoch_terminal」变成了「能继续服务」。

**边界**：NEG 只说明新 ELF 在该条无变更轨迹没有打开新代，**不是**新旧 ELF 在所有输入上逐位相同。

#### 5.2 model_transaction（107–109）

**做法**：直接驱动 vendored acados C API。在**已经用过的** capsule 上通过 `set_p_global_and_precompute_dependencies` + reset 换 30 维 p_global，并分别保存每个模型版本的 warm-start。

接口：`register_version` / `prepare` / `commit` / `solve`。prepare 期间拒绝 solve；commit 应用对应参数；solve 携带模型代际；回切版本可取回自己的 warm book。

**实测（108 批）**：固定 M0/M1 与固定状态/参考序列，切换后相对 fresh M1 的 `u_diff = 0.0`、六维预测状态 `X_diff = 0.0`（门限 1e-8）。6 个组件 case 覆盖若干状态门与 warm 路径。**确实调用了真实 acados 及生产 Backend 对拍，不是 mock 数值。**

生成结构仍是 NX8 / NU2 / N20 / NP6 / NP_GLOBAL30，所以有限数值切换不需要重新 codegen。

**边界（档案自己写得很清楚）**：

- 未实现 GP 学习、数据采集、在线辨识、生产 Worker 端到端激活；
- 未证明任意模型、任意参考、并发和所有故障路径等价；
- 1e-8 阈值的有限正例不能写成完整 capsule/任意输入的逐位等价。

## 5. 三个系统性模式（比结论更值得记）

### 5.1 假通过几乎都出在验证器，不在被测物

这是全档案重复次数最多的失败模式。三个独立实例：

**实例一：91 批的 T2-C「全过」。** 我用文件时间核过：

```
18:44:53  implementation/runs/T2C_OPTA/driver_result.json 落盘   passed = False
18:44:53  driver_events.jsonl
18:45:40  implementation/t2_author/audit_t2.py 被修改
18:48:06  implementation/t2_author/t2_action_contract.py 去重改动加入
18:48:30  postrun/t2c_complete_pass.json 记录「ALL CHECKS PASS」
```

通过结论比 run 晚 4 分钟，比判据晚 3 分钟。用未去重版本审计同一 run 得到 `passed=False`（`receipt_accounting` / `output_accounting` 失败）。而且同一批号下 MPC 根与 research 根的两份 `source_bundle.json` 身份互斥，原始 bundle 不描述实际使用的审计工具。

**实例二：82 批重放 81 批。** 82 批用登记 SHA 副本重放 P01，得到 **12/13、passed=false、rc2**；只有把 `job_received` 加进白名单的未登记版本（`170bf747…`）才 13/13、rc0。而那个版本删掉 Worker 流、把 boundary 改成 expired/native=false 仍全过。

**实例三：124 批的系统性复审。** 见 §6.1，10 项问题里 F124-01/02/04 全是验证器缺陷。

**这些案例的共性**：测试在涨、报告在绿、但**判据本身不拒绝反例**。124 批把它总结成一句可操作的规则：

> 具名反例只有被正确断言拒绝才算捕获。

配套的负面清单同样重要：编译失败、解析异常、未执行、无关前置错误，都**不能**算作变异被捕获。

### 5.2 归因做错比不做更贵

同一个 resume 现象被改了四次名字：

| 批 | 归因 | 判定 |
|---|---|---|
| 94 | 「post-resume 系统恢复超过 5 s drain，是已知架构限制不是 bug」 | **错**。111 批用同一 run 事件流证明真因是单代终态 Epoch（`epoch_terminal@tick3`），779 ms 只是停推前残量；给 6.3 s 观察窗也没有新 job |
| 112 | 「锚老化 / 恢复过渡窗内逐侧拒绝」 | **表述错**。113 批改为「恢复过渡窗内逐侧拒绝」，115 再改为同步历史重置 |

> 跨 run、跨时间域的数值不能混比。

配套的第二个教训是**验收器也可能需要先修**。115 批判定 112 的 runner 既要求不该发生的 clock_epoch 变化，又会把拒绝候选和 `ramp_zero` 输出算成「新窗口接纳」——「未修则任何新 owned run 的结论不可信」。所以 116–121 必须按 S0→S1→S2→S4 重做，而不是直接补跑。

### 5.3 测试数量会掩盖证据层级

同一份文档里会并排出现两种数：

## 8. 对下一步的判断

档案自己的下一步建议（124/126/127）是：

1. 先审**模型事务共享 setter**（纯 packing 可先落位，checked 需先解决工厂 fallback）；
2. 再单独审 **Epoch 生命周期政策**；
3. **B2 只归实验时钟基础设施**，不接实船 clock；
4. 三项不捆绑，各自独立 freeze / 负控 / 有限 owned。

我在此基础上补充三点观察：

**第一，台架复现应提到最前面。** 它成本最低、不依赖任何新资源、直接决定后续一切是否有意义。53 批提出后 70 多批无人执行，这是一个明显的空缺。

**第二，「资源级阻塞」的判断成立，但边界可再审视。** 110 批判定主线到边界（需 plant / RT / GP 数据），这个判断在「M4 阶段资格」这个口径下是对的。但 124 批随后证明：在**不新增任何资源**的条件下，仍有 10 个验证器缺陷可修，且它们直接决定未来任何 owned 运行结论是否可信。所以「到边界」和「可以停下」不是一回事——124 做的正是该在边界处做的事。

**第三，也是最值得警惕的一点：这套档案最薄弱的环节不在控制，在「谁来审审计器」。** 124 是唯一一次真正的独立复审，它一次性挖出 10 个问题，其中 3 个（Q2 悬空引用、RNW 恒真、105 恒真比较）都属于「已通过很久但从未真正拒绝过反例」。126 修完后，E12 依然因过程问题 FAIL_STOP。这说明**复审的密度远低于开发的密度**——从 01 到 123 批，绝大多数批次是自己写实现、自己写审计、自己判通过。

如果只从这份档案里学一件事，我建议是这条：**每 N 批强制插入一次「只做反证、不写实现」的独立复审**，且复审者的验收标准不是「有没有发现 bug」，而是「能不能构造出让现有审计判据说出 passed=true 的错误证据」。124 批做的正是这件事，它拿出来的反例——删掉关闭文件仍 passed、把 generation 改成 99 仍 passed、旧 Proposal 在退役后仍能提交——比任何新增测试都更有价值。
