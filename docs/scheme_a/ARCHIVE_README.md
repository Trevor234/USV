## 二、 归档与路径兼容原则（避免脚本与回读失效）

在方案 A 的历史交付包（如 `delivery_s3_s5_closure_R40_20261104`）中，包含大量严格的绝对路径散列与封签校验：
1. **防止硬编码路径断裂**：部分审计工具与交付清单（如 `S2G.rev08.delivery_manifest.json`）记录了绝对路径 `/home/trevor/MPC/delivery_*`。
2. **推荐归档模式**：
   - **方式一（软链接索引，零风险）**：在阶段子目录中建立指向原始批次的符号链接，保持根目录原件不动，同时拥有清晰的分阶段视图；
   - **方式二（物理迁移 + 根目录软链接保活）**：将批次目录移入对应阶段子目录，并在 `/home/trevor/MPC/` 建立同名软链接指回新位置，既清爽根目录又不破坏既有脚本。

## 三、 后续进行方案 A 时的存储规范

未来进行方案 A 的任何开发、测试、复审与交付时，**禁止在 `/home/trevor/MPC/` 根目录下直接平铺生成新的临时目录或批次包**，必须严格遵循以下存储规范：

1. **命名规范**：
   - 实验过程包：`scheme_A_<主题>_<YYYYMMDD>_<批次号或版本>`
   - 交付归档包：`delivery_<阶段>_<版本>_<YYYYMMDD>`
2. **存放位置判定**：
   - 属于当前正在推进的 S5 修复与新批次：统一存放在 **`08_后续研发与新批次产物/`** 下；
   - 属于对历史特定阶段的补充审计或勘误补丁：存放在对应阶段目录下的 `supplements/` 子目录；
   - 正式通过封签后的新里程碑交付：归入对应交付目录或在 `08_后续研发与新批次产物/` 下建立独立的 `delivery_*` 包。
3. **元数据自闭环**：
   每个新增的批次包必须包含标准的四要素：
   - `CURRENT.md`：当前状态与结论（人读）；
   - `postrun/`：机器可读回执（程序读）；
   - `evidence/`：原始日志、JSON 与重放记录（复核用）；
   - `implementation/`：派生源码与可重放脚本。
