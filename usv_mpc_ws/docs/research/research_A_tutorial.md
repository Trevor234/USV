# 第 1 部 为什么：这个研究要解决什么问题

## 1.1 研究问题的诞生：一次审计发现的"迟到计划被执行"

### 1.1.1 背景：scheme=B 的 5Hz 控制回路怎么工作

NMPC（非线性模型预测控制）的每个控制拍（tick，0.2 秒）做三件事：拿当前状态 → 解一个 4 秒时域的最优控制问题（N=20 步）→ 把最优解的第一拍推力发给推进器。方案B 的配置：状态 6 维 `[x, y, ψ, u, v, r]`（位置/航向/纵荡/横荡/艏摇角速度），双输入 `[T_L, T_R]`（左右桨推力，N），acados SQP_RTI 求解器，预算 **200ms** 内返回。

这个回路平时工作得很好。2026-10-03 的只读审计（`NMPC与安全链路审查_2026-10-03.md`）却在代码里发现了一条致命路径。

### 1.1.2 失败模式逐步拆解

审计发现的代码路径（当时 `mpc_node.cpp:552–577`）：

```
控制拍开始
  │
  ├─ ① 同步调用 solve()          ← 在控制线程里阻塞等待求解完成
  │      （求解器超预算时，整个控制线程被卡住——没有任何人能在这期间发布命令）
  │
  ├─ ② solve() 返回，检查超时
  │      超时函数只把 info.success 改成 false —— 仅此而已
  │
  ├─ ③ 失败计数 <5 时仍发布 u_opt ← 这个解是用"上一拍甚至更早采样的状态"算出来的
  │      （stale state → stale plan：状态已经变了，计划还是旧的）
  │
  ├─ ④ 后端返回前已改热启动缓存  ← 迟到解的轨迹被 shift 进 warmstart，
  │      下一拍求解的初值被污染
  │
  └─ ⑤ 连续失败 ≥5 次才归零      ← solver_hold_threshold_=5
```

主文档把这条链总结为研究 A 的**第一阻塞项**（§3.1 原文）：

> "同步调用求解，再检查超时。超时函数只把 `info.success` 改为 false，默认前 4 次失败仍发布返回的 `u_opt`；到第 5 次才归零。一个数值成功但超过 200ms 的解因而仍可能被下发。后端在返回前已改热启动缓存。"

这里每个环节都值得停一下，因为它们共同构成"**迟到/过期计划被执行**"（late/stale plan execution）这一核心失败模式：

- **为什么"迟到"危险**：200ms 预算不是随便定的——船以 0.8 m/s 前进时，200ms 漂 0.16m；如果求解花了 400ms 才返回，这个解的"第一拍"对应的是 400ms 前的世界。执行它等于闭着眼按旧地图开车。
- **为什么"仅改标志位"不够**：`info.success=false` 只是记了个账，发布代码看的是"有没有连续失败 5 次"，前 4 次照样发。审计注入 250/400ms 延迟的实验证实：迟到候选 `[22,-18]N` 会一路走到 bag。
- **为什么"warmstart 污染"是隐性伤害**：即使本拍拒掉了迟到解，它已经 shift 进热启动缓存——下一拍的求解初值建立在迟到轨迹上，等于脏数据有了后代。
- **为什么"第 5 次归零"也不安全**：归零（双桨推力 0）听起来安全，但船有惯性会继续漂——主文档明确"零推力、低速、HOLD、RTL 都不能直接作为安全证明"（见 1.2 节第 4 条）。

### 1.1.3 为什么简单修补不够

读到这里你可能想：在 `solve()` 后面加 `if (timeout) return old_action;` 不就行了？主文档专门回答了这一点（§3.1）：

> "仅把 `if(timeout) return old_action` 放在同步 `solve()` 后面还不够：求解阻塞期间同一执行线程无法准时接管。监管器要有独立执行上下文；求解器工作者各自拥有 capsule，不能并发修改同一 acados 对象的参数、求解和读解。"

问题的本质是**结构性**的：只要"求解"和"发布"住在同一个线程里，求解卡住 = 发布也卡住。修补只能解决"返回后要不要用这个解"，解决不了"阻塞期间谁来发命令"。这就是为什么研究 A 的答案是架构级的（独立监管器 + worker 分离），而不是补丁级的。

顺带交代结局：这个第一阻塞项后来被抽成独立最小修复，在主文档发布当天（10-03 02:21）就完成并验收了（`NMPC_迟到解_修复与验证报告`：迟到解不再发布、`reset_warmstart()` 连带清污，37 项 GTest 通过）。但修复后的方案B只是"不再执行迟到解"，"独立监管、认证备份、模型切换有效期"这一整套研究问题仍然原封不动地摆在那里——这正是首选A要研究的。

## 1.2 五个"必须纠正的前提"：研究的第一课是破除直觉

主文档 §1.1 列了五条"看起来对、其实错"的安全直觉。这五条是整个研究的思维底座，逐条精讲：

### 前提一："不是任何 GP 均值更新都会使旧物理备份失效"

**直觉版本**：模型更新了，旧的备份（backup）肯定不安全了，得全部重验。

**为什么错**：GP（高斯过程）在线学习改的是**性能均值**——预测"船大概会怎么动"。但安全备份的依据是**误差包络**——"船最多偏这么多"。如果原有固定误差包络仍然覆盖真实动力学，且时间/状态/障碍/执行器条件没变，那么"预测的均值"变了并不改变"真实的动力学集合"。

**白话比喻**：天气预报从"明天 20°C"改成"明天 21°C"——你出门要不要带伞取决于降雨概率的**区间**，不是均值的那个点。均值挪了一点，区间没变，伞的决策不用变。

**研究含义**：把"均值更新"当"安全破坏"会造成伪创新（为不必要的事情设计复杂机制）。D0 诊断专门验证这一点（见 4.2 节）。

### 前提二："拒绝更新也不等于安全"

**直觉版本**：模型不放心就别更新，拒绝更新 = 稳妥。

**为什么错**：真实世界在漂。实际阻尼、推进效率、海流都会随时间变化——旧模型的"紧误差界"（窄的包络）是**基于旧数据算的**，世界变了它就过期了。正确的做法是二选一：扩张"误差年龄界"（承认旧数据、放宽容差），或退回"仍有效的固定宽界"（保守但有效的包络）。两者都失效时，必须报告"保证域外"——明说"我保证不了了"，而不是假装还在保证。

**白话比喻**：超市里的鲜奶。你可以喝（紧界还在保质期），可以退回喝常温奶（固定宽界），但两种都过期了就得承认没奶可喝（域外），不能把过期奶当没过期。

**研究含义**："有效期管理"是研究对象本身——这就是标题里"validity management"的来源。

### 前提三："热启动移位不等于认证备份"

**直觉版本**：求解器有 fallback——失败时沿着上次的轨迹 shift 一步继续发，这不就是备份吗？

**为什么错**：scheme=B 当时的 `safe_fallback_` 只是"沿旧轨迹前移一格、末端补零"。它缺少认证备份的全部要素：当前状态、误差界、障碍、执行器与终端条件检查。主文档原话："当前后端移位旧输入并补零，缺少当前状态、误差界、障碍、执行器与终端条件检查。"

**白话比喻**：认证备份是有体检报告的健康人（知道自己的适用范围）；热启动移位是"上次那个动作大概还能再做一次"——没人检查过它现在还适不适用。

**研究含义**：必须把三个对象分开——**候选解、优化热启动、认证备份**。它们住在不同的存储里，由不同的机制管理（第 2 部展开）。

### 前提四："零推力、低速、HOLD、RTL 都不能直接作为安全证明"

**直觉版本**：出事就停车（推力归零）/悬停（HOLD）/返航（RTL），停车总是安全的吧？

**为什么错**：船会继续漂。惯性和海流让"零推力"的船继续移动；欠驱动船（没有侧向推进器）也不能默认"停在世界坐标某个小圆域里不动"。一个"安全动作"必须是**被验证过**在该状态下安全的动作，不是"听起来温和"的动作。

**白话比喻**：高速路上爆胎，"松开方向盘"不是安全策略——车还在动，结果取决于物理，不取决于你放不放手。

**研究含义**：备份库里的每个策略都要"用当前状态集合、已知 plant 版本和执行器条件重算未来 4s，保留实际可行项"（主文档 §6），不能预存一个"通用安全动作"。

### 前提五："GP 方差变小、求解器返回成功、任务完成、历史平均求解很快，分别都不能代替安全或实时证明"

**直觉版本**（四个子句各是一种常见错误）：
- "GP 方差变小了 → 模型更准了 → 更安全了"——方差小只说明**在这个数据点附近**预测一致，不说明包络覆盖了全局；
- "求解器返回 success → 没问题"——求解器说"我算完了"，不说"我算的对"，更不说"我按时算完的"；
- "任务完成了 → 过程是安全的"——结果好不等于过程合法（可能刚好没撞）；
- "历史上平均求解 80ms → 实时性没问题"——平均值对最坏情况零约束，硬实时看的是最坏值。

**研究含义**：这条前提直接塑造了第 4 部的度量设计——四类指标（实际约束/执行证书/性能/数据计算）分开报告，谁也不能顶替谁。

## 1.3 GO / CONDITIONAL / NO-GO：研究开始前先划清能声称什么

主文档 §1.2 对每项拟议内容做了创新可行性分级。这张表本身就是一种研究纪律——**先声明"我做不到什么"，再开始做**：

| 项目 | 判断 | 含义 |
|---|---|---|
| 基于当前平台实现可复现原型 | **GO** | 先补提交时序、数据契约与备份检查；不依赖重新训练 PPO |
| 单船静态障碍下有限时域机制实验 | **CONDITIONAL** | 先有已知有效扰动范围、可接续备份、独立区间检查和实际执行日志 |
| 使用经验 GP 界缩小保守性 | **CONDITIONAL** | 时序留出校准、工况覆盖、年龄失效与宽界回退先通过；结论限定为经验结果 |
| 严格递归可行性 / 无限时域安全 | **NO-GO** | 未建立安全终端集合/控制律、统一有效误差事件与持续接续条件 |
| "首次 GP+NMPC 用于 USV""首次更新门禁" | **NO-GO** | **已有明确先例，不能用作贡献** |
| 独特的执行器、数据年龄、动作保持与切换充分条件 | 待论证 | 要与成熟方法逐条比较；仅 ROS 集成按系统/经验贡献定位 |

其中 NO-GO 的两条最值得展开——因为它们是"查新"的结果，防止把别人做过的当自己的：

- **递归可行性 / 无限时域安全**：真正的"永远安全"证明需要安全终端集合（不变集）+ 控制律 + 统一的置信条件。Maiworm 等与 Koller 等的工作在这条线上已经走得很远（见 2.4 节），本课题第一轮不具备建立这些数学基础的条件，所以明确不做、也不声称。
- **"首次"类主张**：主文档 §6.4 原文点名——"Maiworm 等已提出以候选最优代价不增接受在线更新，且说明不限于 NARX 或 GP；Koller 等已有安全回返、GP 外包络和安全/性能预测分离。其安全定理依赖已知安全控制器、鲁棒不变安全集及统一置信条件。因此'更新门禁、旧解接续、双模型'自身不是新增贡献。"

那剩下的真正贡献空间在哪？主文档的原话（§6.4）：

> "本课题只有在**执行器与保持时间、非平稳误差年龄、模型/备份切换条件**形成新的可计算充分条件，或在正确强基线下形成可解释系统证据时，才有独立论文价值。"

翻译成白话：前人解决了"更新要不要接受"（门禁）和"回不回得去"（安全回返），但"**一个被认证的动作允许保持多久**（执行器界）、**一条旧数据的老化如何定量**（非平稳年龄）、**模型和备份在什么条件下切换**"这三件事的可计算充分条件，还有做文章的空间——要么做出新的充分条件（理论贡献），要么在正确的强基线对照下给出系统级证据（实证贡献）。

**当前执行决策**（主文档结尾，一句话总结全局）：

> "当前执行决策：GO 于 P0/P1；CONDITIONAL 于静态障碍有限备份与 GP 安全缩界；严格安全/递归证明保持未完成状态。"

这个决策到今天（10-08 证据）仍然有效：P0 已完成闭包，P1 在影子模式实施中，CONDITIONAL 的两项还没启动，NO-GO 的承诺依然没有被悄悄违反。

# 第 2 部 原理：候选—验证—提交—执行机制

第 1 部说了"为什么"，这一部讲"设计成什么样"。全部机制出自主文档 §4–§6。

## 2.1 核心架构：五个角色和"三个必须分离的对象"

### 2.1.1 数据流全景

主文档 §4.1 的架构（Mermaid 图的线性化版本）：

```
带采样时间的状态与执行反馈
        │
        ▼
┌──────────────────────────┐
│ S 状态快照与数据质量门禁  │ ← 拒绝 NaN/全零四元数/过期/混源的状态
└──────────┬───────────────┘
           │
     ┌─────┴─────┐
     ▼           ▼
┌─────────┐  ┌──────────────────────────┐
│ B 动态   │  │ G 异步残差学习/候选模型    │
│ NMPC 候选│◄─┤   → 不可变模型快照 M      │
│ 工作者 N │  └──────────────────────────┘
└────┬────┘
     │ 候选计划
     ▼
┌──────────────────────────┐
│ V 独立轨迹/可达管验证     │ ← 用当前状态集合在整个保持区间上重算
└──────────┬───────────────┘
           │ 验证通过的候选 + 证书
           ▼
┌──────────────────────────┐     ┌────────────────────────┐
│ C 提交与备份监管器         │ ◄── │ B 认证备份库与有效期    │
│ （唯一决策者）             │     └────────────────────────┘
└──────────┬───────────────┘
           │ 联合决策（同拍只发一次）
           ▼
┌──────────────────────────┐
│ E 唯一推力执行出口        │ → VRX 左右推进器（Float64 话题）
└──────────┬───────────────┘
           │
           ▼
     逐拍证书与拒绝原因日志 L
```

演进路线（主文档原文）："最初没有 PPO 节点，也没有真实 GP；由既有 B 生成候选。后期 PPO 通过相同接口输出建议左右推力，安全 NMPC 可以最小化与建议的差并生成备份。"——也就是说 RL 策略（scheme=C）最终也会接入这个管线，但身份是"建议者"而非"执行者"。

### 2.1.2 三个必须分离的对象

第 1.1 节的失败模式里，"热启动缓存"身兼三职是根因之一。主文档 §3.1 给出结构处方：

> "必须分离三个对象：**候选解、优化热启动、认证备份**。后两者不能共用一个可被求解线程随时写入的缓存。提交监管器在截止时间前选择已验证候选或仍有效备份；迟到结果最多作为下一拍重验证的输入，不按旧初值直接执行。"

三个对象各自的身份：

| 对象 | 是什么 | 谁写 | 生命期 |
|---|---|---|---|
| **候选解** (candidate) | 本拍求解器算出的新计划 | worker 算，验证器验，监管器决定用不用 | 一拍内 |
| **优化热启动** (warmstart) | 给求解器加速的初值猜测 | 后端在成功求解后更新 | 跨拍延续，可被 reset |
| **认证备份** (certified backup) | 带证书的应急计划（策略库计算、验证过、有适用条件） | 只有验证流程能认证 | 带有效期，过期作废 |

关键在最后一列：备份不是"上次的解"，而是**提前用备份策略库（保持航速/左转/右转/减速）重算并验证过的计划**，每个都带"在什么状态范围/误差界/障碍版本/执行器条件下有效"的证书。

## 2.2 固定执行 tick：把"求解快慢"和"执行节奏"解耦

### 2.2.1 方案

这是整个架构最精巧的一环。主文档 §4.4：

> "首版采用**固定执行 tick**：在 t_k 执行由上一周期验证好的 q_k；后台用 q_k/已验证备份把状态集合传播到 t_(k+1)，针对下一执行 tick 求解。t_k+150ms 只原子提交候选，不提前发布；t_(k+1) 再快速核对测量是否落在预测初始集合、执行锚点与证书是否有效，随后发布 q_(k+1)，保持到再下一 tick……启动第一拍须已有有效初始备份。"

用时间轴展开（T = 200ms 一拍）：

```
        t_k            t_k + 150ms          t_(k+1)
        │发布 q_k            │提交截止            │发布 q_(k+1)
────────┼────────────────────┼────────────────────┼────────▶
        │                    │                    │
  拍 k 的后台工作：      候选必须在此之前       拍 k+1 的后台工作开始
  - 冻结状态/参考        完成验证并提交；       （为 t_(k+2) 求解）
  - worker 求解          过了就作废，
  - 独立验证             只能用备份
  - 为 t_(k+1) 准备
```

在 t_k 时刻发布的东西（q_k）是**上一个周期就验证好的**——所以发布动作本身不需要等任何求解，监管器的 tick 线程永远不会被求解阻塞。求解器再慢，慢的只是"下一拍有没有新候选"，不是"这一拍有没有命令发"。

### 2.2.2 预算分解与"150ms 设计值"

Ts=200ms 一拍的钱怎么花（主文档 §4.4 原文）：

> "初始分配：状态/参考准备 15ms，候选求解与 GP 均值计算 80ms，独立验证 40ms，提交/发布 15ms，剩余 50ms 作调度和预留。**150ms 为本拍候选提交截止设计值，不是本次测量结果，也不等于真船硬实时保证。**"

注意最后那句的诚实声明：150ms 是**设计值**（15+80+40+15=150），实验要测的是实际 P50/P95/P99/最大值——预注册的验收阈值"端到端 P99≤150ms"是**筛选指标**（§9.2："P99 达标不等于硬实时证明"）。

还有一个反直觉的细节，主文档专门强调："不得在 150ms 直接发布，再把到 200ms 的 50ms 首段当成完整 200ms 离散预测。"——提前发布会让"计划的第一步"和"实际的第一个保持区间"错位，离散动力学模型（dt=0.2s）就全对不上了。宁可让命令等到 t_(k+1) 整点发。

### 2.2.3 时钟分工

物理时间和计算时间必须分开计量（§4.4）："物理积分/障碍运动用仿真时间；计算截止用 steady 时钟。" 仿真时间会暂停/回退（Gazebo 特性），拿它当截止计时器会出灵异事件；steady 时钟（单调钟）只认同一 boot 内的流逝。P0 数据契约把这套分工做成了三个显式时间域（见 3.1.3）。

## 2.3 状态机与每拍决策序

### 2.3.1 计划的六种状态

主文档 §4.3：

> "CANDIDATE → VALIDATED → ACTIVE；另有 BACKUP_ACTIVE、EXPIRED、OUT_OF_DOMAIN、UNVERIFIED_EMERGENCY。必须区分'候选被拒绝'与'现活动证书已经无效'。"

白话对照：

| 状态 | 含义 |
|---|---|
| CANDIDATE | worker 刚算出来，还没验 |
| VALIDATED | 独立验证通过，拿到证书，排队等提交 |
| ACTIVE | 已提交，正在被执行 |
| BACKUP_ACTIVE | 没有合格候选，正在执行某个仍有效的认证备份 |
| EXPIRED | 证书到期（年龄/条件失效），不能再接续 |
| OUT_OF_DOMAIN | 超出声明的保证域，只能报告，不再声称安全 |
| UNVERIFIED_EMERGENCY | 工程应急动作（如归零）——明确标注"未验证"，不冒充安全 |

最后两个状态的存在本身就是纪律：宁可承认"我现在保证不了"（OUT_OF_DOMAIN / UNVERIFIED_EMERGENCY），也不把未验证的动作包装成安全的。

### 2.3.2 每拍七步决策序

主文档 §4.3 给出的顺序（每拍固定流程）：

1. **快照**：一致的状态/最终动作/障碍/误差年龄快照 + 域检查；
2. **先保底**："优先确认当前备份还能覆盖本拍及接续，不等待新优化耗尽预算"——先确认退路，再谈前进；
3. **模型快照**：worker 对每个候选冻结模型快照，"每个 worker 独占 solver 实例"；
4. **独立验证**：验证器"从当前状态集合在整个保持区间 + 备份尾段上重算可达外界"——不是信求解器的自评，是自己再算一遍；
5. **提交比对**：核对 state_sequence、模型/包络/障碍版本、截止时间、计划激活 tick、执行锚点——**任何一项对不上就不提交**；
6. **原子激活**："待激活模型+新备份+证书"作为一个原子组提交，激活时再核状态集合与锚点，"同一拍只发布一次联合决策对应的左右命令"；
7. **拒绝路径**：候选不可用 → 执行仍有效的旧备份或有效宽界备份；都没有 → 记录域外 + 声明的工程应急。

第 5 步的"版本比对"是防**混版执行**的：禁止出现"新均值 + 旧误差界 + 旧备份"这种拼盘组合（主文档："禁止读取混合的'新均值、旧误差界、旧备份'"）。第 2 步的顺序设计（先备份后候选）意味着：哪怕候选验证完全失败，拍也不会空转。

## 2.4 认证备份库与有限时域安全

### 2.4.1 备份不是"上次那个解"

主文档 §6 定义了备份策略库：

> "备份先采用反馈跟踪的'保持航速/左转/右转/减速'策略库，推荐目标航速 0.4 或 0.6m/s、目标艏摇率 0 或 ±0.2rad/s，推力仍按 ±25N/80N/s 限制。每个策略用当前状态集合、已知 plant 版本和执行器条件重算未来 4s，保留实际可行项；无法验证的策略不进入认证库。"

四个策略听起来平平无奇，但要点在"**用当前状态集合重算**"——备份不是预存的轨迹，是每次需要时按当下条件现算现验的。这呼应 1.2 节前提四：不存在"通用安全动作"。

### 2.4.2 h_max：每个计划的保质期

"验证器对每个计划计算 h_max，监管器在保持时间达到该值之前接续。" 一个计划被验证时，同时算出"它最多允许保持多久"（误差传播随时间发散，保持越久偏得越远）。监管器盯着表：接近 h_max 还没有新候选/备份接续，就必须切换。200/400ms 的保持是 D2 诊断的**受控试验变量**——不是随便选的数。

### 2.4.3 有限时域安全命题（§6.3 白话翻译）

主文档的正式命题草案：

> "若有效外包络、初始状态集合、障碍占据集和执行器界成立，备份反馈序列及其终端满足条件，且提交后的模型/包络/状态/时间与验证快照一致，则按该证书执行首段并以更新后的状态集合接续，得到相应有限时域安全；有持续安全终端及接续存在性时，再讨论递归执行。"

逐句拆开：

- "若有效外包络…成立"——**前提**：我们声明的误差界、初始状态的不确定性集合、障碍占据范围、执行器极限，这些输入都真实有效；
- "备份反馈序列及其终端满足条件"——**前提**：备份的每一步和终点都在约束内（4 秒内不撞、不越界）；
- "提交后的模型/包络/状态/时间与验证快照一致"——**前提**：执行时的世界和验证时的世界是同一个世界（没有混版、没有过期）；
- **结论**：那么按这个证书执行首段、并用更新后的状态集合接续，能保证**有限时域内**（那 4 秒）的安全；
- "有持续安全终端及接续存在性时，再讨论递归执行"——想从"4 秒安全"升级到"永远安全"，需要不变集那套数学，那是 NO-GO 的部分，第一轮不做。

这就是标题里"有限时域"的准确含义：**不声称永远安全，只声称在证书覆盖的时间窗内、在声明的条件下安全**。诚实的边界比夸大的承诺更有科学价值。

## 2.5 误差年龄与非平稳性：这套研究独有的核心概念

### 2.5.1 固定宽界与性能中心的分离

主文档 §5.3 建立了集合代数。安全的一步映射写成：

$$F(x,q) \in F_0(x,q) \oplus B\,G_0(x,q) \oplus E_0$$

- $F_0$：名义模型（我们写的 Fossen 动力学）；
- $G_0$：**固定宽界**的三维速度增量残差集合——"真实动力学与名义模型的差，最多落在 $G_0$ 里"。它是**安全的基石**，第一轮不缩不小；
- $B \in \mathbb{R}^{6\times3}$：把三维速度残差嵌入六维状态；
- $E_0$：覆盖离散化、位置/航向积分、估计误差的集合。

### 2.5.2 重心化等价：为什么改均值不动安全

GP 学习的是性能中心 $\mu_v$（残差的预测均值）。更新后性能中心变成 $F_0 + B\mu_v$，误差集合必须**重心化**：

$$W_v = B(G_0 - \mu_v) \oplus E_0$$

主文档："在精确集合语义下，中心相加后仍得到相同物理集合。首阶段 GP 只改性能，固定宽界安全集合不缩小。"

白话：把"误差集合的中心"跟着均值挪，物理上覆盖的范围**一模一样**。$(F_0 \oplus BG_0) = (F_0 + B\mu_v) \oplus B(G_0 - \mu_v)$——平移不变。这就是前提一（均值更新不破坏安全）的数学形态。D0 诊断的全部内容就是验证这个等价在实现里真的成立。

### 2.5.3 年龄扩张：旧数据怎么定量折旧

学到的界 $L_v$ 只在快照时刻 $t_v$ 准。用旧界要加"年龄扩张"：

$$L_v(t) = L_v(t_v) \oplus D(t - t_v)$$

$D(\cdot)$ 是随时间增长的膨胀集合。世界漂得越久，学到的紧界越不可信，界就得放得越宽。策略阶梯（主文档 §5.3）：

1. 声明工况内 $L_v$ 失效 → 退回固定宽界 $G_0$（保守但有效）；
2. 超出 $G_0$ → **不能**以拒绝更新恢复保证，必须报域外。

D1 诊断专门测这条链（阻尼 20–40s 缓慢漂移 + 数据年龄 2/5/10s，见 4.2 节）。

### 2.5.4 GP 学什么、不学什么（P3 预告）

- **输入/标签**：$z = [u, v, r, T_L, T_R]$（5 维），标签 $y_k = \nu_{k+1} - [F_0(x_k, q_{exec,k}; \Delta t_k)]_\nu$——**真实速度增量减名义模型预测的残差**，三个独立输出（m/s, m/s, rad/s）。注意"加入离散速度预测时不再乘 Ts"；
- **样本准入的洁癖**：只收"固定 tick、Δt∈[0.198, 0.202]s、区间内单一最终命令"的样本；控制输入用 $T_{exec}$（实际执行的推力）而非 PPO raw 或 NMPC 优化输出——安全层接管或限幅后，策略建议值不代表实际发生了什么；
- **更新节奏**：1Hz 异步快照、每批最多 5 个合格标签——"更新开销不阻塞 5Hz 执行监管器"；
- **数据规模**：首批 60 段 × 60s × 5Hz ≈ 最多 18,000 个区间标签，直行/左转/右转/S 形/推力阶跃/限率过渡六类各 10 段，按完整 episode 60/20/20 分训练/校准/测试（防止相邻区间跨集合泄漏）。

## 2.6 影子模式：先当影子，再谈接管

主文档对 P1 工作包 3 的要求：

> "首先加入影子模式：记录本拍会接受/拒绝什么，仍沿原 B 执行，明确不声称已安全。随后在可控仿真场景接管执行。"

影子模式（shadow mode）= 监管器全程运行完整的决策逻辑（准入、验证、提交判断），但**不发布任何物理命令**——船仍由原方案 B 控制。监管器在旁边记录："如果我说了算，这一拍我会接受/拒绝这个候选，理由是什么。"

这解决了研究方法学的一个死结：**新机制的第一次运行不能拿安全性当赌注**。影子期积累的"接受/拒绝决策流"既是调试证据（拒绝原因码分布暴露实现 bug），也是后续对照实验的基线数据。配套的诚实声明（§6）："影子模式可先用开环序列诊断，但开环多步误差会扩大；闭环备份证书须包含反馈控制律及输入可达界，不能验证一条名义序列后随意加反馈。"

实际实施里影子模式还有一个技术细节：监管器锚定（anchor）在 legacy B 节点的 F5 AppliedControl 流上——用它作为"上一拍实际执行了什么"的真值来源（见 3.4 节）。

# 第 3 部 实施：从数据契约到监管器代码

原理是应然，实施是实然。这一部讲首选A落地成了什么：P0 的数据契约（F1–F5），P1 的两进程架构（regulator + worker），以及代码里每个机制"防的是什么事故"。代码引用均为实际路径。

## 3.1 P0 数据契约：先把"发生了什么"变成可信数据

研究的输入是数据。如果连"这一拍到底执行了什么命令、用哪个状态算的"都说不清，后面的安全分析全是沙上塔。P0 数据契约（`p0_data_contract.md`，schema `p0-contract-v1`）就是给执行过程装上的黑匣子。

### 3.1.1 三条研究消息

**共同身份块**（每条消息都带）：`schema_version="p0-contract-v1"`、`run_id`、`producer_instance_id`、`baseline_id`、`config_hash`、`sequence`、`clock_epoch`、`steady_clock_domain`。它们回答"谁、在哪次运行、哪个基线、第几条、哪个时钟纪元"——离线检查器靠它们切分时间、检测重启、拒绝跨纪元拼接。

**① StateSnapshot（/research/state）——"这拍用的状态是原子的"**

字段：身份块 + 六维状态 `state_6=[x,y,psi,u,v,r]` + odom 原戳/接收序号/接收与冻结 steady 时间 + frame id/child frame id + clock 值/年龄/状态 + `valid` + `quality_reason`。

语义保证：**六维状态完全来自同一条 ground-truth odom**。这防的是"跨时刻拼装"——旧代码里 odom 回调写 x,y,ψ,u,v，IMU 回调直接覆盖 r，两个回调来自不同时刻，拼出来的"状态"在物理上从未存在过。契约下这种状态会被标记 `state_kind=controller_mixed`（P1 的 CycleTiming 里），原子状态标 `odom_atomic`。

无效处理的原则很讲究："NaN/Inf、全零四元数、frame 未知等会使快照无效；无效数值的有限占位必须连同 valid=false 解释，不能当训练值。"——宁可留一个诚实的无效占位，不留一个看起来正常的假数。

**② CycleTiming（/research/cycle）——"这拍的时间都花在哪了"**

字段：`timer_entry → state_copy → reference_ready → solve_start → solve_end → publish_end` 全链 steady 时间戳 + 求解前实际使用的 `controller_state_6` + `state_kind` + 接受的 odom/IMU 身份（序号+戳）+ `backend_time_ms` vs `budget_ms` + `deadline_miss` + `rejection_reason` + `solve_invoked`。

它是 1.1 节失败模式的"仪表盘"：同步 solve 阻塞多久、迟到没迟到、拒了什么、为什么拒，全在这条消息里。注意边界声明："计时为本机可观察回调/参考/solve/发布调用链，不能称传感器到执行器完整端到端。"——没有传感器时间戳，就不冒充有。

**③ AppliedControl（/research/control/applied）——"物理上到底发了什么"**

字段：`event_semantics="publisher_command"` + 请求推力 `requested_n` vs 映射/限幅后 `final_n` + 左右两路各自的发布成功标志、起止 steady 时间、发布时刻的 sim 时间/clock epoch/年龄 + `map_scale`/上下限 + 前次锚点 + 三个显式的能力边界布尔。

关键语义："每次记录窗口内发布尝试都有新 sequence，相同 N 值也不合并……左成功右失败形成 partial 事件，保留异常，不伪造联合成功。"——左右桨是两个话题，左成功右失败是真实可能的，契约要求如实记录而不是装作"发过了"。

### 3.1.2 五个永久 false 的旗帜

AppliedControl 里五个布尔**永远为 false**，直到有独立证据：

| 旗帜 | 为什么是 false |
|---|---|
| `plant_acceptance_observed` | 发布调用成功 ≠ Gazebo/实机接受了 |
| `force_measured` | 没有力传感器，发的不是实测桨推力 |
| `execution_atomicity_proven` | 左右两话题的"原子性"无法证明 |
| `exact_execution_timing_available` | 无 Header 的 Float64 话题没有执行时刻 |
| `gp_labels_ready` | GP 标签合同未闭合（P3 未做） |

这五个 false 是第 1.2 节前提五的工程化：每个"不能声称的能力"在数据结构里占一个显式位置，而不是散落在文档里。谁想拿这些数据声称更多，先得把对应的 false 变 true——而那需要真证据。

### 3.1.3 三个时间域与 20ms 配对窗

"wall timer、steady 接收时间、ROS 仿真时间混用"是审计发现的时序乱源（§3.5）。契约的处方——三个域各司其职，**不混算**：

| 时间域 | 来源 | 唯一合法用途 |
|---|---|---|
| **系统接收时间** | recorder 的 DDS 到达时钟 | bag 时间域内的事件配对 |
| **显式 /clock** | 消息里带的仿真时间 | 仿真物理时间区间（发布间隔的 sim 时刻） |
| **steady 时钟** | CLOCK_MONOTONIC | 同一 boot 内的计算/发布耗时 |

**20ms 匹配窗**：同一 bag 时间域内，左右两路 Float64 推力与 AppliedControl 事件的配对只在 20ms 接收窗内进行——这是 DDS 传输抖动下的唯一合理配对尺度。配套警告："低实时率仿真下，同一个仿真时间窗可能覆盖多次墙钟发布，因此不能把 system receive 的 20ms 门槛直接用于仿真时间。"

### 3.1.4 F3 补丁：四元数门禁

审计发现 `quaternion_to_yaw` 对全零四元数算 `atan2(0,1)=0`——垃圾输入变成"航向 0"混进控制。F3 门禁（现在在 `p1_input_core.hpp` 的 `admit_odom` 里）：分量有限性检查之后、yaw 转换之前，**拒绝平方范数 < 1e-12 的四元数**。"无效接收保持可观测，但被接受的控制状态、身份与 odom 新鲜度不变"——拒绝的是这一个样本，不是整个系统。

### 3.1.5 录制流程与门禁

8 步 pilot 流程（`p0_contract_recording.md`）把"录制"也做成了带门禁的流程：隔离 domain/partition → 未武装启动 → `capture_p0_runtime_context.py` 图门禁（每个必录话题恰有一个 recorder 订阅、研究消息与推力各有唯一原 B 发布者，返回非零就不许武装）→ 核对参数 → 武装 → 录 60s → 源端正常收尾等队列排空 → 停 recorder → 跑只读检查器 `check_p0_contract.py`（核对实扫计数/身份/时间，生成合同报告）。

武装语义值得记：`research_logging_armed` 默认 false，只有图检查通过才置 true——"按实际计数验收，不用 graph 发现代替 bag 完整性"。

## 3.2 F1–F5：P0 实际长成的样子

主文档的 P0 是一个阶段（3–5 个工作日、六个工作包）。实施时它长成了五个带独立冻结基线的子包（`.sgh-research/baselines/`）：

| 子包 | 日期 | 做了什么 | 为什么插入 |
|---|---|---|---|
| **F1** three_repairs_original | 10-04 | 三项提前修复（迟到解/ONNX 缩放/PPO bag 动作）后的原样冻结 | 研究的"时间零点"：此后所有改动都可归因 |
| **F2** publisher_contract | 10-04 | 三条研究消息 + 录制入口 + 直行/左转/右转 60s pilot | 数据契约本体 |
| **F3** quaternion_gate | 10-04 | 四元数门禁 + 模型一致性（291 例 Python/C++/native acados 对拍，最大差 ≤8.9e-16）+ profile 列语义勘误 | 堵住垃圾四元数；确认三条实现算同一个模型 |
| **F4** config_reference | 10-05 | plant/nominal 配置分离 + 实际参考观测（ReferencePrediction 消息）+ 单因素 probe（plant.mass→17.04kg） | 控制器认知与仿真真相解耦：能单独改船的真实参数而不动控制器假设 |
| **F5** atomic_freeze | 10-05 | 求解资格与输入原子冻结（state_lock 下的二次检查 + build_frozen_reference） | 消除"求解期间回调改状态"的竞态——P1 的直接前置 |

F4 的"配置独立"值得多说一句：它维护三份配置——`controller_nominal`（控制器以为的船）、`plant_actual`（仿真里真实的船）、`generated_effective_plant`（生成器实际生效的）。三者分离后，"模型失配"从混沌概念变成可精确控制的实验变量（改 plant.mass 一个数，其余全冻结）。

F5 的原子冻结解决的是微妙但致命的竞态：求解器正在用状态 x 算，状态回调线程同时把 x 改了——解算的是半个旧世界半个新世界。冻结代码在 `mpc_node.cpp` 里标注 `P1_ATOMIC_DYNAMIC_FREEZE_V1`：取 `state_lock_` 后**重新跑一遍资格检查**（双检），再合成状态、快照研究出处、构建冻结参考——状态与参考在同一临界区内定格。锁序有讲究："Standby 后取输出锁再取状态锁；先释放再进 standby"（防死锁）。

## 3.3 P1 代码走读：两个进程、一条时间线

P1 的实施代码在 `usv_mpc_ws/src/usv_research_safety_cpp/`（新包，扁平布局：regulator.cpp / solver_worker.cpp / p1_*.hpp 与测试同层）+ `usv_mpc_cpp` 的共享核心（`p1_input_core.hpp/cpp`）。两个进程：

```
┌─────────────────────────┐   /p1/solve_job (reliable, depth 1)   ┌──────────────────────┐
│  p1_regulator           │ ─────────────────────────────────────▶ │  p1_solver_worker    │
│  · prepare 线程(构建任务) │                                        │  · 独占一个 acados     │
│  · tick 线程(唯一决策者) │ ◀───────────────────────────────────── │    capsule            │
│  · Sink 日志线程         │   /p1/solve_candidate                 │  · 单工作线程(一次一个  │
│  · 模式: shadow/execute │   /p1/worker_capability (200ms 信标)   │    job，新任务顶替旧的) │
└───────────┬─────────────┘                                        └──────────────────────┘
            │ execute 模式: 唯一物理发布出口
            ▼
   VRX 左右推力 / legacy B 的 AppliedControl（shadow 模式锚定对象）
```

### 3.3.1 契约即代码：p1_full_contract.hpp

监管器启动时加载一份 JSON 契约（schema `p1-execution-contract-v2`），`load_contract(file, hash)` 先验 SHA-256，再逐字段校验。契约里钉死了全部参数：N=20、dt=0.2s、T_ns=200ms、deadline_ns=150ms、Q/R/Rd/Qf、命令界 ±25N、rho=80N/s、hold_ns=600ms、激活容差、odom/imu 年龄门 100ms、RTF 窗 0.95–1.05、看门狗 1s……并且 `parse_unique_contract` 拒绝重复 JSON 键。

最有意思的一个字段：`physical_execute_release_enabled=false`，注释"physical execute release is disabled until B5/M4"——**物理执行的解锁本身是硬编码关闭的**，没过 B5/M4 里程碑，代码里写死不让任何配置打开 execute 模式。这是把"影子模式纪律"焊进了代码，而不是靠自觉。

### 3.3.2 tick 线程：200ms 一个的绝对节拍

tick_loop 用 CLOCK_MONOTONIC 绝对时间睡眠（`planned = origin + tick·T`），不吃累积漂移的亏。每拍动作序列：

1. **跳拍检测**：due_tick > tick 时记 `scheduler_skipped_ticks`，作废候选与准入，`normal_complete_=false`——跳拍是异常，必须可见；
2. **时钟暂停确认**：`clock_pause_confirm_ns` 触发后 bump 调度 generation、重置 origin——仿真暂停/恢复不是普通事件；
3. **活动任务看门狗**：超 `active_watchdog_ns`（1s）→ `unusable_locked("active_watchdog")`，策略 "stop_submit; supervisor owns finite TERM/KILL"；
4. **锁下快照**：状态、参考、保持输入历史、发布历史、锚点、五元 Version{task, model, config, schedule, epoch}、odom/imu 身份、sim 时间、mixed 标志、paused、rtf；
5. **取已提交的准入 Ticket**（`admission_.take(tick, now)`）和已注册的候选；
6. **决策**（下面细说）；
7. **发布**（仅 execute 模式；shadow 模式无物理发布者）。

### 3.3.3 决策序与拒绝原因码

监管器对候选的检查按固定顺序（`eligible()` → 候选检查 → 提交时复查），每一步失败都有一个具名原因码。这是理解整个系统最好的入口——**每个码对应一次真实的事故假设**：

**资格层**（复用 `usv_mpc::input_eligibility` 共享核心）：`no_odom` / `odom_timeout` / `no_path` / `no_state` / `state_timeout` / `disarmed` / `wrong_mode`，然后是监管器自己的：`nonfinite`（状态里有 NaN/Inf）、`mixed_source_age_or_skew`（混源状态且年龄/偏斜超标）、`clock_missing_stale_paused`、`rtf_unaligned`（实时率飘出 0.95–1.05）、`profile_pair_incomplete`、`invalid_path`、`unknown_anchor`。

**候选层**：`version_mismatch`（五元 Version 对不上——防混版）、`publication_history_check`（锚点历史完整性）、`activation_history_or_time`（名义传播到目标时刻的历史/时间对不上）、`activation_state_mismatch`（实测状态 vs 预测初始集合超出激活容差 `[0.25,0.25,0.15,0.3,0.2,0.15]`）、`candidate_mapping_changed`（候选经 map_vrx 映射后变了——映射不该改命令）。

**提交时复查**（锁下最后一刻）：`activation_input_changed_during_validation`（验证期间输入变了——2.2 节竞态的最终防线）、`tick_jitter_at_commit`、`target_sim_mismatch`、`command_check`（限幅 + 相对锚点的变化率 `|u−a.n| ≤ rho·(now−a.time)+1e-9`）、`shutdown`。

**候选准入**（`candidate()` 回调里）：资源界 → `valid_job`（foreign/invalid_time_order/shape_or_time_contract/nonfinite/unknown_or_invalid_anchor…）→ `foreign_worker` → `solver_failed` → `nonfinite_or_timing` → `first_control_mismatch`（首控制 vs u_prediction 差 >1e-8）→ `prediction_initial_mismatch`（x_prediction vs target_state 差 >1e-7）→ `job_echo_mismatch` → `native_timing_order`（freeze ≤ worker_receive ≤ solve_start ≤ solve_end ≤ now 的时序链）→ `run_unusable` → Admission 的 `wrong_tick` / `version_mismatch` / `time_contract` / `late` / `duplicate` / `cutoff_closed` / `ready_slot_full` → `late_registration_completion`。

全通过才 `control_source="candidate"`；否则走 fallback：`hold`（hold_ns=600ms 内且原因可接受时保持锚点）或 `ramp_zero`（按 rho 限率衰减向零）。

### 3.3.4 准入的三个线性化点：ready → committed → taken

`p1_admission.hpp` 的 Admission 类实现了一个精密的提交协议，常量 `T=200000000, DEADLINE=150000000`：

- **register_ready**：worker 的候选要在 `now ≤ deadline`、target==current_tick+1、版本一致、非重复、截止未关、就绪槽空时注册——这是"就绪"点；
- **cutoff(now)**：`now > deadline` 时把 ready ticket **提交**（committed）——注意代码注释"Registration, cutoff and activation have different linearization points; closing at equality is forbidden"（关闭点禁止取等号，防边界竞态）；
- **take(target, now)**：`target` 匹配且 `now ≥ target_ns` 时把 ticket 交给 tick——这是"激活"点。

三个点分离意味着：注册（worker 说"我好了"）、提交（监管器说"过截止了，定稿"）、激活（tick 说"到点了，用它"）各自原子，任何一步失败都不影响已完成的步骤。这就是 2.2 节固定 tick 方案的代码形态。

### 3.3.5 worker：独占 capsule、绝不重启

`solver_worker.cpp` 的纪律：

- **独占**：整个进程只有一个 `AcadosBackend` capsule，一个工作线程一次只消费一个 Pending job——"capsule 由单 worker 独占"（防并发改同一个 acados 对象）；
- **任务序**：job_id 必须严格递增（`duplicate_or_reordered`）；迟到于 deadline 的任务在进 native 前就拒（`late_before_native` / `pending_expired_before_native`，`solver_invoked=false`）；
- **故障注入**：`test_delay_ms`（求解后延迟发布）/`test_native_block_ms`（native 前阻塞屏障），受 `fault_injection_enabled` 门控且有上界（≤10000/≤60000ms）——D2 诊断的实验工具；
- **失败终态**：任何异常或 native 结果失败/无效 → `terminal_numerical_failure`，策略 "quarantine_this_run_no_restart"——**本 run 内绝不重启**。监管器通过 pidfd 检测死亡。一个算错的 worker 重启后大概率还是错的，隔离比复活安全；
- **能力信标**：每 200ms 发 `WorkerCapability`（schema `p1-worker-capability-v1`）：backend、矩阵布局、horizon_steps=20、pid、completed/active/pending 计数、fatal 标志。

### 3.3.6 三个小而硬的机制

- **pidfd 存活检测**（`p1_worker_liveness.hpp`）："Pin the process identity once. No /proc scan, wait, signal or restart occurs in either control commit. A dead pidfd stays dead even if numeric PIDs recycle."——用 Linux pidfd 钉住进程身份，数字 PID 被系统复用也骗不过它；且检测绝不在控制提交的关键路径上做扫描/等待/信号；
- **能力租约**（`p1_capability_lease.hpp`）："Trusted callback receipt lease only."——租约只证明"收到过信标"，明确不证明新鲜度或求解进度；超时即终态。注释里那句自我限定很典型："WorkerCapability v1 has no packet sequence/send time: this is neither source freshness nor solve progress."；
- **RTF 时钟窗**（`p1_clock_window.hpp`）：400–600ms 窗口内解耦的 (receive, sim) 锚点对估计实时率；"No valid estimate survives a short window, receive gap, invalid chronology, or clock epoch change"——窗太短/接收断档/时序非法/纪元变更，任一条件毁掉估计。

### 3.3.7 prepare 线程：任务怎么构建

构建 SolveJob 的关键步骤：取锁下快照 → `propagate_publisher_nominal` 把冻结状态（odom 戳时刻）用**保持输入历史**经 RK4×4 名义传播到目标 tick（代码注释强调："This is a point prediction, never a measured plant input or reachable-set bound"——这是点预测，不是实测也不是可达集界）→ `build_frozen_reference`（与 legacy 同一函数）→ 填身份/世代/时序（deadline=origin+150ms，target=origin+200ms）/锚点/历史（≤256 条）→ `reset_warmstart` 判定沿用 legacy 的 135° 规则（`|normalize_angle(psi−ref)| > M_PI·0.75`）。提交门在锁下：shutdown / worker_unusable / worker_unvalidated / source_failed / version_changed_before_submit / tick_changed_before_submit / deadline_expired_before_submit。

## 3.4 影子模式怎么"锚定"现实

shadow 模式的监管器没有物理发布者，但它要做出和 execute 模式**完全同构**的决策——这要求它知道"现实里上一拍执行了什么"。答案是锚定 legacy B 的 F5 AppliedControl 流：

- 要求来源 `baseline_id=="F5_20261005_atomic_freeze_01"`、`event_semantics=="publisher_command"`、steady_clock_domain 里 run/boot 匹配、sequence 连续（断档/纪元变更时 `legacy_history_reset`）；
- 有了这个锚，监管器的 hold/ramp_zero/变化率检查都能在影子下"空转验证"——决策流全程可审计，而船永远在 legacy B 手里。

这就是影子模式的完整闭环：**同一套决策代码、同一个时间线、零物理风险**。等 B5/M4 里程碑过了、`physical_execute_release_enabled` 打开，这套代码才第一次真正碰到推进器。

# 第 4 部 验证：预注册的实验设计

研究的方法学核心：**所有假设、场景、阈值在跑实验之前就写死**（主文档 §8"预注册"），防止"先看结果再编故事"。这一部速览这套设计。

## 4.1 五个假设与证伪条件

| 假设 | 内容一句话 | 怎么证伪 |
|---|---|---|
| **H0** | 固定真实包络下，单纯性能均值改变不必破坏物理备份 | 完整条件一致时仍出现集合不等价——先判实现/传播错误，而非创新成立 |
| **H1** | 版本+截止时间管理减少不合法执行 | 全机制仍执行非法候选；或修正时序的强基线已同样解决且无其他增益 |
| **H2** | 非平稳误差年龄管理有独立价值 | 固定有效宽界以同成本/进度解决全部案例；或年龄界没有可信来源 |
| **H3** | GP 性能补偿有用且不破坏执行保证 | 不改善留出/跟踪，或收益全来自默认同模型差异、错误动作幅值或额外算力 |
| **H4** | 机制在冻结 PPO 建议下仍有效 | 只在某策略/特定轨迹成立——收窄结论，不称策略通用 |

注意每个证伪条件都预先堵住了"自欺"的退路：H0 的证伪被引导去查 bug 而不是宣称创新；H1 要求强基线对照（击败原仓库 B 不算数）；H3 明确"收益必须不能来自算力差异"。

## 4.2 场景、诊断与对照

**场景**：R0 直线（单位/时延门禁用）→ R1 擦边障碍（中心 (12,1.5) 半径 0.5，**是否可行由有效可达界决定**，不预设答案）→ R2 正挡障碍（必须绕行，纯跟踪 B 可能被拒）→ R3 固定路径 × 初始扰动分层。障碍几何：船体圆 0.7m + 障碍 0.5m + 余量 0.2m = 名义中心间距门槛 1.4m，"还要加位置可达管、估计误差和区间占据裕度"。

**诊断**（每个瞄准一条假设）：
- **D0** 均值切换：残差均值在 0 / ±[0.02, 0, 0.01] 间切——"这些是人工性能偏置，不是学习结果"，验证重心化等价（H0）；
- **D1** 年龄与漂移：阻尼 20–40s 缓变 + 数据年龄 2/5/10s，比较紧界/年龄扩张/固定宽界（H2）；
- **D2** 动作保持与执行器：计算延迟 250/400ms × 执行滞后 0/0.15/0.30s，"先找出明确反例，再做同初值重复，不按新方法有利程度挑 seed"（H1）。

**基线与消融**：B0 原仓库 B（"只诊断既有缺陷；击败它不足以说明研究贡献"）→ **B1 修正时序的固定宽界备份（"必需强基线"）** → B2 加性能 GP → B3 代价接受规则 → B4 Koller 式安全回返（无正确安全集时"标为有限时域实现"）。消融：A-full / A-no-age / A-no-hold / A-no-applied（用建议而非最终执行动作作标签）/ A-no-version。公平性："所有强方法得到相同传感信息、plant 先验、障碍、初值、输入限制、CPU 线程数和端到端预算。"

**参数矩阵要点**（§8.2）：plant 质量/阻尼/推力效率 ×0.8/1.0/1.2（"只改 plant，控制器名义冻结"）；执行器时间常数 0/0.15/0.30s；传输延迟与计算延迟分开；海流 (0,0)/(0,0.15)/(0,15) m/s；状态年龄 0.05/0.20/0.40s（"必须由保持输入传播到当前时刻，不能只放宽 timeout"）；漂移 t=20–40s 阻尼倍率 1.0→1.2；跳变 t=20s 推力效率 1.0→0.8；seed 初筛 0–4 / 确认 0–9 / 冻结场景 100–119。

**运行规模**：P0/P1 回归 12 类×5seed×30s=60 次；D0 90 次；D1 120 次；D2 180 次；确认集 2 场景×4 工况×6 方法×10 seed=480 次×60s；GP 数据 60×60s。跑之前先 10 次 pilot 估墙钟（"单批初始墙钟预算 6 小时、VRX 日志预算 10GiB"）。

## 4.3 验收阈值与统计纪律

预注册的工程通过标准（§9.2，原文数字）：

- **零容忍项**："迟到、混版、过期动作执行数为 0；每一物理动作均可追溯至联合决策。"
- **数值容差**：幅值/增量 1e-4 N；动力学一致性位置 1e-4 m、yaw 1e-4 rad、速度 1e-4 m/s 或 rad/s。且"若积分误差已大于容差，应先改积分/验证方法并重新冻结，不能事后调容差抹去违规"；
- **几何**：违反按"真实有效船体/障碍边界"计数，"不以宽松数值容差容许碰撞"；
- **时延**："候选提交初始 ≤150ms；端到端 P99≤150ms 为筛选指标，同时报告最大值。超过预算只能接续有效备份，不能继续发迟到新解。P99 达标不等于硬实时证明。"
- **效用**：首轮进度 ≥ 对应 B1 的 80%，确认集到达率目标 ≥95%——"这些是效用筛选阈值，不是已经取得的结果；同时报告不可行初值组，禁止删除其失败"；
- **最硬的一条**："有效条件内确认组期望没有无法解释的实际违反；只要出现一次'接受证书但实际违反'，停止概率/安全表述，定位误差、时序或传播原因后重做相关门禁。"——一次不一致就停牌整改。

统计纪律（§9.3）：同 seed 配对比较、95% 置信区间；"零事故不等于概率保证。若 n 个真正独立 episode 中 0 次事件，单侧 95% 二项上界为 `1−0.05^(1/n)`；例如 n=100 约 2.95%"——不跑 100 次不撞就宣称 97% 安全。

控制能耗的定义也预注册了：`sum(TL²+TR²)×Δt`，单位 N²s；"没有电流/电压测量就不称实际能耗"。

## 5.3 诚实边界：这套系统现在不能声称什么

把散落各文档的"不能声称"收拢成一张清单（这是本研究的灵魂部分）：

1. **不能声称硬实时**——150ms 是设计值，P99 达标是筛选指标；"150ms 为本拍候选提交截止设计值，不是本次测量结果，也不等于真船硬实时保证"；
2. **不能声称执行原子性/实测推力/植物接受**——五个永久 false 旗帜直到有独立证据；
3. **不能声称递归/无限时域安全**——只有有限时域命题，安全终端集合未建立（NO-GO 项）；
4. **影子模式不能声称任何安全性**——"明确不声称已安全"；影子下的决策流只证明机制在运行，不证明它是对的；
5. **名义传播只是点预测**——"This is a point prediction, never a measured plant input or reachable-set bound"；
6. **零事故不等于概率保证**——二项上界公式管着表述；
7. **本地主文档是旧版快照**——Windows 侧 10-05 已扩至 68,815 字节并新增两份子计划文档（P0 执行计划、P1 原子冻结），本地 docs/research 是 56,050 字节版；引用主文档时注意版本。

**一句话现状**：机制的全部零件（契约、准入、截止、激活、看门狗、影子锚定）都已存在且在 38 类故障注入下空转验证，但**还没有一次真正的物理执行**——而这正是下一里程碑（B5/M4 → execute 解锁）要挣来的资格。
