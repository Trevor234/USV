# NMPC 迟到解仍被执行：最小修复计划

日期：2026-10-03。状态：**已实施，节点回归、正常VRX短程与250/400ms Gazebo故障录包验证通过**。执行结果详见同目录《NMPC_迟到解_修复与验证报告_2026-10-03.md》。  
基线：`/home/trevor/USV`，分支`codex/scheme-c-rl`，提交`1e5becae622782526f20fc93928339133c94ec23`的已核验源码快照。实施前复查当前Git差异，避免覆盖后续改动。

## 1. 修复目标与范围

**超过求解调用预算返回的候选，不再作为本拍新控制发布，也不继续作为有效热启动使用。** 在节点层增加一个明确的候选拒绝分支，复用现有发布和失败计数流程，不先引入异步求解、GP、认证备份或新ROS包。

必须区分两个问题：

- 本补丁解决：求解返回后已经判超时，却仍执行其控制量。
- 本补丁尚不解决：同步求解阻塞时，节点不能在200ms截止时刻主动发布回退动作。要解决按时接管，需要独立执行线程/进程，属于后续改造。

“保持上次命令”是工程回退，不是经过避碰验证的安全备份。本计划不赋予它安全保证。

## 2. 已核验原因

`usv_mpc_ws/src/usv_mpc_cpp/src/mpc_node.cpp:552–577`：

1. 同步调用`mpc_->solve()`，得到`u_opt`与`info`。
2. `enforce_solve_deadline_()`仅把`info.success`改为false。
3. 默认连续失败不到5次时，`u_opt`没有替换，仍送入`publish_dynamic_output_()`。

此外，acados在返回成功候选前已更新`X_warm_ / U_warm_ / u_prev_`，见`src/acados_backend.cpp:299–305`。只替换输出而不清热启动，迟到计划仍会留在后端；而`reset_warmstart()`又会清空`u_prev_`，清理后必须重新写入下发等效推力。

## 3. 最小改动清单

### 3.1 缓存上一条发布入口量与下发结果

在节点增加或复用以下成员：

- `last_commanded_thrust_`：上一条送入`publish_dynamic_output_()`的入口推力。
- `last_applied_thrust_`：该函数返回的下发等效推力，用于求解器输入变化率锚点；不是实测推进器推力。
- `has_last_command_`：缓存是否属于当前连续控制段且可重复发布。

每次正常控制、后端回退或HOLD目标通过统一发布路径下发后更新缓存。初始化、进入STANDBY、释放控制时使缓存失效，避免重入ACTIVE重放旧航段命令。

**重发使用`last_commanded_thrust_`，不能直接重发`last_applied_thrust_`。** 发布函数会进行VRX缩放或RC映射。例如scale=0.5时，入口`[10,6]N`发布为`[5,3]N`；保持输出应重发`[10,6]`，再次映射`[5,3]`会变成`[2.5,1.5]`。

### 3.2 用完整调用耗时判准入，保留原诊断字段

节点用`std::chrono::steady_clock`在`mpc_->solve()`调用前后计时，得到`solve_wall_time_ms`，覆盖后端参数装配、求解、取解和缓存更新。

保持现有`SolveInfo.solve_time_ms`语义与结构，用于后端诊断；不修改跨ABI的`SolveInfo`布局。私有截止检查函数增加节点调用耗时参数，准入规则为：

```text
当 max_solve_time_ms > 0：
    solve_wall_time_ms > max_solve_time_ms
    或 backend solve_time_ms > max_solve_time_ms
    => deadline_miss
```

保留`>`边界与`max_solve_time_ms<=0`关闭截止检查的原行为。非有限/负的后端计时应判为诊断无效并拒绝候选，避免NaN比较漏判；计时异常与真正超时使用不同原因码。节点使用明确的`time_rejected = deadline_miss || invalid_timing`选择替代命令，不能对计时异常又只改`success=false`后继续发布原候选。

完整调用计时仍不包含参考构建、回调排队、发布传输或执行器响应，因此不称端到端硬截止时间。

### 3.3 显式选择本拍发布命令

保留返回候选作为诊断变量，另设`selected_command`，按以下表选择：

| 条件 | 发布选择 | 后端处理 |
|---|---|---|
| 未超时且求解成功 | 返回候选 | 保留正常热启动，失败计数归零 |
| 未超时且正常求解失败 | 原后端fallback | 保留既有行为；达到HOLD阈值仍按原零目标 |
| 超时或计时无效，失败计数1–4且缓存有效 | `last_commanded_thrust_` | 丢弃被拒绝候选的热启动 |
| 超时或计时无效，尚未有有效缓存 | 明确零推力命令 | 丢弃被拒绝候选的热启动 |
| 失败计数达到默认5次及以后 | 原HOLD零目标 | 保留原失败策略并清热启动 |

超时分支必须覆盖“后端成功但超时”和“后端失败且超时”；计时无效也走明确拒绝分支。这些情况下均不再发布本次返回量。失败计数每拍只加一次。

无缓存时发布`publish_dynamic_output_(Zero)`；**不要误用`publish_zero_dynamic_output_()`**，后者在RC模式是释放覆盖通道，不等价于发送明确中立命令。

### 3.4 清迟到热启动，恢复执行锚点

一旦拒绝迟到候选：调用`reset_warmstart()`，不发布该候选的预测轨迹。随后按选定命令统一发布，并调用：

```text
applied = publish_dynamic_output_(selected_command)
mpc_->set_applied_control(applied)
更新 last_commanded / last_applied / has_last_command
```

执行锚点回写必须在热启动清理之后。另在下一次`solve()`前、所有本节点的预求解热启动重置之后，若缓存有效，再用`last_applied_thrust_`恢复锚点，防止现有航向偏差重置分支把锚点再次清零。新控制段无有效缓存时沿原初始化语义，不假称已测得真实推力。

迟到候选不进入新预测Path，不更新“上一条发布命令”缓存。清理后恢复的锚点是实际发布函数返回值，不是迟到候选首拍。

### 3.5 状态与日志只补必要信息

保留已有`solve_time_ms`、`deadline_miss`、`success`、`fail_count`、`hold`字段，补充：

- `solve_wall_time_ms`：节点测得的完整求解调用耗时。
- `control_source`：`solver`、`backend_fallback`、`repeat_last_command`、`zero_no_history`或`hold_zero`。

保留`solve_timeout`错误前缀兼容已有状态判断，错误文本同时显示调用耗时与后端耗时。输出字段记录选定发布入口量与下发等效量，不能把迟到候选当作实际命令。日志不把重复命令称为“安全备份”。

## 5. 最小验收用例

测试同时观察物理输出/发布入口和`set_applied_control`，不能只检查`info.success=false`。逻辑测试使用可注入计时值，避免依赖墙钟抖动；另保留一次模拟阻塞的集成用例。

| 用例 | 输入/条件 | 必须得到的结果 |
|---|---|---|
| 正常成功 | 调用20ms，候选`[12,8]` | 发布候选，计数归零，正常热启动 |
| 后端计时偏小 | 后端报1ms，调用250ms，旧入口`[10,6]`，候选`[−20,20]` | 发布旧入口，迟到候选完全不进入输出 |
| 后端报告超时 | 注入调用短但后端报告250ms | 兼容准入规则仍拒绝，不依赖某一种计时 |
| 无效计时 | 后端报NaN/Inf或负数 | 明确拒绝、原因不同于超时，不能只改success后仍发布候选 |
| 边界/关闭 | 精确200ms；阈值0或负 | `>`规则保持；关闭时不启用时间门禁 |
| 首次即超时 | 缓存无效 | 走明确零命令发布，不释放RC通道 |
| 连续超时 | 1–4次、5次及以后 | 前4次重发缓存，第5次走原HOLD零目标；计数不重复增加 |
| 非单位VRX缩放 | scale0.5或2，包含限幅 | 重发与上一下发值一致，无二次缩放 |
| RC映射 | 同一入口经映射/量化 | 重发同一PWM覆盖命令，下发等效锚点一致 |
| 锚点与热启动 | 超时后再调用正常solve | 调用次序为reset→发布→set_applied；下一求解锚点正确，迟到轨迹未被复用 |
| STANDBY再进入 | 缓存有旧航段动作，释放后首拍超时 | 缓存已失效，不能重放旧动作 |
| 普通失败 | 未超时，后端给fallback | 原失败处理保持，不能误判为迟到 |
| 恢复 | 超时后及时成功 | 可恢复候选输出，不因旧超时永久HOLD |

VRX短程：正常直行约30–60s，与补丁前输入/轨迹结果对比；再用测试专用假求解器注入250/400ms，录制左右输出与`/mpc/status`，证明没有迟到候选被发布。不要为验证此问题直接做真船试验。

**通过标准：**所有超时用例中迟到候选执行数为0；缓存、下发等效锚点和状态日志一致；普通成功/失败路径无意外变化；原NMPC相关回归通过。测试与仿真完成前不标记“已修复”。

## 6. 明确保留的限制与后续任务

1. 同步求解仍可长时间阻塞，执行端在这段时间继续保持旧命令；本补丁不是硬实时接管。
2. 重复旧命令没有新状态/障碍认证，也可能在超时期间变得不合适。
3. 保留原第5次HOLD零目标，会保留可能的推力突降/变化率越界；零推力也没有避碰保证。限率减推力应作为独立补丁，避免本次同时改变故障策略。
4. 清热启动可能增加下一拍冷启动耗时；回归记录连续超时率与恢复时间，不能只看一次成功。

后续优先级：先单独修故障降推力的率限与锚点一致性；再做独立执行监管与固定tick提交，才能解决阻塞期间的按时接管。认证备份、障碍验证与模型切换研究仍按主方案后续阶段开展。
