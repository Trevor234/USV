# 模块 2：时间 —— 三个时钟域为什么不能混算

对应代码：`mpc_node.cpp` 的 clock 观测、`CycleTiming.msg`/`AppliedControl.msg` 时间字段、`check_p0_contract.py` 配对窗、`p1_clock_window.hpp`。

## 2.1 时钟基础

| 时钟 | 遇到 NTP 校时 | 重启后 | 用途 |
|---|---|---|---|
| realtime（墙钟） | 会跳 | 归零 | 报"几点几分" |
| monotonic（单调钟） | 绝不跳 | 归零 | **算时间差唯一正确选择** |
| sim time（ROS 仿真时间） | 会暂停/回退/跳变 | 重启 | 物理计算 |

- 单调钟保证后取 ≥ 先取，但**跨重启不可比**——所以 `steady_clock_domain = boot_id + ":steady_clock"` 必须绑定每条消息（[research_logger.hpp:78-81](../src/usv_mpc_cpp/include/usv_mpc_cpp/research_logger.hpp#L78-L81)）。
- `use_sim_time: true` + `/clock` 话题：节点内 `now()` 取 sim 值。**控制节拍刻意用 `create_wall_timer`**（[mpc_node.cpp:73](../src/usv_mpc_cpp/src/mpc_node.cpp#L73)）——求解预算是真实计算时间，节拍不随仿真慢而慢。研究文档的表述："物理积分用仿真时间；计算截止用 steady 时钟。"

## 2.2 一条消息的三个时刻

```
Gazebo 产生 odom(sim=T) ──DDS──▶ recorder 写 bag ──▶ mpc_node 回调执行
  ④ header.stamp = T            ② bag 记录时间       ③ 接收时刻(steady)
```

| 时刻 | 谁写 | 回答 |
|---|---|---|
| header.stamp（sim 域） | 发布者 | 数据描述仿真世界哪个瞬间 |
| 接收时刻（steady 域） | 订阅者回调 | 我何时拿到它（新鲜度） |
| bag 记录时间（recorder 域） | rosbag2 | 录制器何时看到它（**事后配对唯一依据**） |

三域合同（P0 契约脊柱）：

| 域 | 唯一合法用途 | 禁止 |
|---|---|---|
| ① sim | 物理区间、传播起终点 | 算耗时、配对 |
| ② steady（同 boot） | 计算/发布耗时差分 | 跨 boot、与 sim 相减 |
| ③ bag 接收 | 同 bag 内事件配对（20ms 窗） | 当作任何一端的真实发生时刻 |

**跨域相减是重罪**：steady 零点与系统钟零点在两个进程里不同、且系统钟会被 NTP 调——两个数除各自内部排序外没有任何可比性。

## 2.3 时钟异常三态 + 纪元

[mpc_node.cpp:84-98](../src/usv_mpc_cpp/src/mpc_node.cpp#L84-L98) `research_clock_`：

- **reset**（sim 回退）→ `epoch+1` —— 时间轴断了
- **jump**（>5s 跳变）→ `epoch+1` —— 同上
- **paused**（值相等）→ **不换纪元** —— 时间轴连续只是冻结

纪元的语义是"**同一条时间轴**"，不是"有没有异常"。检查器据此拒绝跨纪元拼接区间。测试 `ClockPauseResetAndJumpRemainDistinctEpochs`。

## 2.4 20ms 配对窗

问题：bag 里 Float64 推力与 AppliedControl 事件**没有共同 ID**，如何证明对应？答案只能在 ③ 域：同一次 publish 的两路 DDS 消息到达同一 recorder 的间隔在传输抖动量级。

[check_p0_contract.py:410-455](../../scripts/check_p0_contract.py#L410-L455) 四条铁律：

1. **开区间候选必须唯一**——等值重复报 ambiguous，"values cannot resolve ambiguity"
2. **不可复用、不可乱序**
3. **先定候选、后比数值**（顺序反了就是作弊）
4. armed 跨度之外的记录保留计数但不做完整性声明

为什么窗不能放 sim 域：低 RTF 时同一 sim 窗覆盖多次墙钟发布；同一次发布的两条消息 sim 时间可完全相同——配对只能发生在"实际观察到先后到达"的 recorder 域。

## 2.5 RTF 实时率估计

[p1_clock_window.hpp](../src/usv_research_safety_cpp/p1_clock_window.hpp)（45 行全文）：400–600ms 滑窗，`RTF = Δsim/Δsteady`，合法窗 [0.95, 1.05]。四类失效任一毁掉估计（头注释）："No valid estimate survives a short window, receive gap, invalid chronology, or clock epoch change"——**宁可没有估计，不要错误估计**（下游拿 `rtf_unaligned` 拒绝码）。

## 小结

1. 算差分用单调钟、对账用接收钟、算物理用仿真钟——混用即错。
2. 纪元 = 同一条时间轴：回退/跳变换，暂停不换；跨纪元/跨 boot 不许拼接。
3. 配对铁律：先时间后数值、候选唯一、不可复用。

## 自测（含答案）

**Q1：生产端 `clock_age_ns` 未收到 clock 时为 -1，检查器要求非负且 not_received 时 sim/receive 为 0——为何至今没炸？**
A：armed 门禁链挡住了——`capture_p0_runtime_context.py` 要求先观察到 clock 才许 arm，sanctioned 流程下不存在"clock 未到而日志已 armed"的状态。绕过门禁手动 arm 才会踩（fail-closed 但报错误导）——两侧约定应择机对齐。

**Q2：ClockWindow 与 research_clock_ 的跳变阈值都是 5s，巧合吗？**
A：不是。`research_clock_` 的 5s 区分"正常流逝"与"时间轴断裂"（决定换不换纪元）；ClockWindow 的 5s 判定"时序非法"（决定 RTF 估计作废）。两者语义同源（时间轴连续性），阈值共用是刻意的对称——但注意它们分属两个进程/两层检查，若未来只改一处会造成观测(observation)与估计(estimate)对"跳变"的判定不一致。

**Q3：直行 pilot 发布间隔 min=130ms（中位 200ms），最可能是什么？**
A：仿真暂停后恢复的一次追赶——暂停期间 wall timer 继续触发但被调度压后，恢复时一拍提前。若是 reset，特征是 sim 时间戳回退+epoch 递增+区间断开（end_unknown），不是间隔缩短。

# 模块 3：实时性与 deadline —— 迟到解问题

对应代码：`enforce_solve_deadline_`、`run_dynamic_mpc_` 拒绝链、`p1_admission.hpp` 的 `fallback()`、`p1_capability_lease.hpp`、regulator tick 循环。

## 3.1 deadline 的物理意义

船 0.8 m/s × 200ms = 0.16m/拍。求解 400ms 才返回 → 解的"第一拍"对应 0.32m 之前的世界。**迟到的正确结果价值为零甚至为负**。MPC 每拍解一个最优化问题，"大概率快、偶尔慢"——必须假设解偶尔迟到并提前决定对策。

## 3.2 旧代码四连击事故（2026-10-03 审计）

```
① 同步 solve 阻塞控制线程 → ② 超时只改 success 标志
→ ③ 失败<5 次仍发布 u_opt（迟到候选 [22,-18]N 实测进了 bag）
→ ④ solve() 返回前已把迟到解 shift 进 warmstart（污染有后代）
→ ⑤ 第 5 次才归零（零推力也不安全——惯性漂移）
```

**为什么"在 solve 后加 if"修不好**：只要求解和发布同线程，阻塞期间没人能发命令。这是 P1 拆进程的动机（模块 7）。

## 3.3 墙钟 vs 后端双计时

后端自报耗时不含调度抢占/缺页/降频——**判迟到只能看墙钟**（模块 2 的单调钟）：

```cpp
// mpc_node.cpp:828-831
const auto solve_start = std::chrono::steady_clock::now();
auto [u_opt, info] = mpc_->solve(current_state, reference);
const double solve_wall_time_ms = ...steady_clock::now() - solve_start...;
```

判据结构（[mpc_node.cpp:716-738](../src/usv_mpc_cpp/src/mpc_node.cpp#L716-L738)）——**先非法性后超时**：

- 计时 NaN/Inf/负（含预算自身）→ `solve_timing_invalid`，**即使预算禁用也拒**（fail-closed；测试 `InvalidTimingFailsClosedEvenWhenBudgetIsDisabled`）
- 墙钟**或**后端任一超限 → `solve_timeout`

**fail-closed vs fail-open**：安全门禁异常时按失败处理（可能误杀），可用性机制才可 fail-open。

## 3.4 降级策略谱系

| 策略 | 物理代价 | 适用 |
|---|---|---|
| repeat-last | 命令基于旧一拍状态 | 短时超时首选 |
| hold（600ms） | 误差随保持时长累积 | 候选暂缺窗口 |
| ramp-zero | 温和刹车，服从 80N/s | hold 过期后 |
| zero | **推力阶跃，违反变化率约束** | 最后手段 |

B 节点四分支（[mpc_node.cpp:835-869](../src/usv_mpc_cpp/src/mpc_node.cpp#L835-L869)）：迟到→repeat-last（`reset_warmstart()` 连污一起清）；数值失败但及时→后端回退解；连续 5 次失败→hold_zero。`control_source` 全程标注（solver/repeat_last_command/zero_no_history/hold_zero/backend_fallback/standby_release/shutdown_zero）。

P1 的 ramp-zero（[p1_admission.hpp:131-136](../src/usv_research_safety_cpp/p1_admission.hpp#L131-L136)）：`out = copysign(max(0,|a.n|−rho·Δt), a.n)` —— 从锚点出发、斜率恰为 80N/s 的直线衰减，**变化率约束被数学精确满足**。锚点 unknown 时输出 0——不知道起点时，零是唯一不撒谎的值。

## 3.5 warmstart 污染与锚点恢复

`reset_warmstart()` 会连带清掉后端的 previous-input 锚点。135° 航向重置后须在 solve 前恢复锚点（[mpc_node.cpp:795-801](../src/usv_mpc_cpp/src/mpc_node.cpp#L795-L801)），且用 `last_applied_thrust_`（映射后的实际值）——**锚点必须与真实执行对齐**。

两本账：`last_commanded_thrust_`（发布输入，repeat-last 用——同样输入过同样映射，幂等）vs `last_applied_thrust_`（实际下发，锚点恢复用——ΔT 约束管执行）。用反了：scale=0.5 时 repeat applied 会**几何衰减**（12→6→3，测试 `NonunitVrxScaleAndClampAreNotAppliedTwiceOnTimeout` 钉死）。

## 3.6 看门狗与租约

- **活跃任务看门狗**（1s）：worker 声明"在算 job X"，超时未完成 → 卡死判定。
- **能力租约**（600ms 回执窗口）：**只证明"最近收到过身份合法的信标"**——不证明新鲜度、不证明求解进展（头注释自我限定）。失效是**终态**，不可在线恢复——恢复可能建立在错误世界观上。
- 数字关系：**hold(600ms) ≤ lease(600ms) ≤ watchdog(1s)**——信任不得长于侦测。

## 3.7 绝对节拍调度

[regulator.cpp:255-265](../src/usv_research_safety_cpp/regulator.cpp#L255-L265)：`planned = origin + tick·T`，绝对时间睡眠不吃累积漂移；处理超一整拍时 `due_tick` 计算落后量、**直接跳到当前拍并显式记账** `skipped_ticks`——不补拍（补拍=执行更过期的计划）、`normal_complete_=false`（本次运行完整性作废）。

## 小结

1. 两块表缺一不可：后端量"计算多贵"、墙钟量"世界等多久"——判迟到看墙钟，计时非法本身就是故障。
2. 拒绝迟到解要连毒一起清：u_opt 不发、warmstart reset、锚点用实际执行值恢复。
3. 节拍与处理解耦：绝对锚定 + 跳拍显式记账，"补拍"永远不做。

## 自测（含答案）

**Q1：repeat-last 用 commanded、锚点恢复用 applied，为什么不能反？**
A：见 3.5——repeat commanded 幂等（重过映射不变）；repeat applied 二次缩放。锚点用 applied 对齐执行；用 commanded 会让 ΔT 约束起点高于真实执行。

**Q2：锚点 unknown 时直接 0，与"不瞬间丢大推力"矛盾吗？**
A：不矛盾——ramp 需要已知起点，unknown 时从 a.n 衰减等于从编造起点做物理不成立的衰减。原则准确表述："不瞬间丢**已知的**大推力"。

**Q3：hold 600ms / lease 600ms / watchdog 1s 的依赖？**
A：hold≤lease≤watchdog。hold 是盲信窗口，lease/watchdog 是侦测窗口——**信任不得长于侦测**。hold 改 2s 时，卡死 worker 要 1s 才被揭发，其间已保持过期命令 1s。hold_ns 因此在 `pending_final_calibration` 里。

# 模块 4：并发与 C++ 系统编程

对应代码：`run_dynamic_mpc_` 锁段、`enter_standby_`/`safe_shutdown` 锁序、`research_logger.hpp` 全文、`p1_worker_liveness.hpp`、测试注入架构。

## 4.1 竞态基础

- **数据竞争 = UB**（不是"可能读到旧值"）——编译器可假设它不发生。
- 三种形态：丢失更新、撕裂读、**TOCTOU**（检查时刻 vs 使用时刻——本项目头号敌人）。
- mutex 引入两个新问题：**死锁**（解法：全局锁序）与**持锁做慢事**（纪律：临界区只做内存操作）。
- `std::atomic` 只保护单个标量——**两个 atomic 的一致性它管不了**，多值整体一致必须 mutex。

## 4.2 C1 事故：一行注释里的海难预案

[kinematic mpc_node.cpp:479-481](../src/usv_mpc_kinematic_cpp/src/mpc_node.cpp#L479-L481)：

```
旧时序：lock → can_solve_(路径300点✓) → unlock
         → [path 回调: clear()] → lock → build_reference_(空路径→全零参考)
         → solve(朝原点的"最优"解) → 船调头驶向地图原点！
```

三个细节：**窗口每次任务结束都打开**（规划器发空路径时）；**全零参考是合法输入不报错**（[p1_input_core.cpp:49](../src/usv_mpc_cpp/src/p1_input_core.cpp#L49) 空路径返回零矩阵）；代价不对称（纳秒 vs 掉头）。

修复（`P1_ATOMIC_DYNAMIC_FREEZE_V1`，[mpc_node.cpp:747-781](../src/usv_mpc_cpp/src/mpc_node.cpp#L747-L781)）：**check→拷贝→构建**同一临界区（"冻结"）；solve 在锁外（慢活绝不进临界区）。同时修复状态撕裂（六维一次定格）。

## 4.3 锁序：output → state

`enter_standby_` 先拿 `control_output_mutex_` 再（内部函数）拿 `state_lock_`；控制线程持 state 锁时要进 standby 必须**先解锁再进**（[mpc_node.cpp:752-753](../src/usv_mpc_cpp/src/mpc_node.cpp#L752-L753) 注释）——主动打破环形等待。

**函数自足原则**：`publish_standby_status_` 读共享状态时自己拿 state 锁（[:1096](../src/usv_mpc_cpp/src/mpc_node.cpp#L1096)）——不指望调用者的锁。

## 4.4 原子关机

```cpp
shutting_down_.store(true);                          // ① 原子旗（无锁立即可见）
std::lock_guard output_lock(control_output_mutex_);  // ② 夺输出锁
publish_zero_dynamic_output_();                      // ③ 关机零推力
research_->stop(true);                               // ④ 日志 flush（耗时，可接受——此时无并发发布者）
```

控制线程两道岗哨（solve 前/solve 返回后各查一次 `shutting_down_`）——solve 阻塞中按 Ctrl-C：关机零推力先发，迟到解返回后被岗哨拦截（迟到+关机后复活双重拦截）。测试 `ShutdownDuringSolveCannotRepublishOrReviveCachedControl` 用条件变量门栓做**受控交错**。

## 4.5 有界队列：`research_logger.hpp` 逐段

```
控制回调(热路径)           logger 线程              recorder
enqueue ──lock+move──▶ [deque≤1024] ──▶ publish ──▶ bag
  满→++dropped              │
  (sequence 照常递增!)       └─ 排空后写 summary (tmp+rename)
```

- **构造**：验证身份 → 占目录（必须不存在）→ 读 boot_id → 建 publisher → **最后**起线程。
- **enqueue（14 行）**：`msg.sequence = ++s.generated` 在锁内、**先分配后判容量**——满了丢弃但序号已消耗，bag 里出现缺号 = 丢弃可观测（"宁可诚实地缺，不要完美地假"）。开销：一次 lock + move + 计数器 + notify。
- **工作线程**：`queue_.empty() && closing_` 才退——**stop 语义是排空后退出**；publish 失败只计数不杀线程。
- **stop 幂等**（`if (closing_) return` 防二次 join=UB）；join 在锁外（工作线程退出前还要拿锁写 emitted——锁内 join 自锁死）。
- **normal_end** = 正常停止 ∧ armed ∧ 无发布错误 ∧ 无中断拍——四项合取写进 summary。
- `context_` 共享指针持住 ROS context——析构竞态用所有权解决。

## 4.6 pidfd：进程身份公证

[p1_worker_liveness.hpp](../src/usv_research_safety_cpp/p1_worker_liveness.hpp)（34 行）：`syscall(SYS_pidfd_open, pid, 0)` 返回绑定该进程的 fd；进程死后 fd 上 POLLIN **永久保持**——"A dead pidfd stays dead even if numeric PIDs recycle."。检查用 `poll(fd, 0)` **零超时**——不停顿、不发信号、不 wait（"No /proc scan, wait, signal or restart occurs in either control commit"——检查出现在决策关键路径上也不许有副作用）。

## 4.7 注入式测试

私有构造 + `friend class MpcControllerNodeTestAccess`（[mpc_node.hpp:73-76](../src/usv_mpc_cpp/include/usv_mpc_cpp/mpc_node.hpp#L73-L76)）：测试拿到全访问权，生产二进制无测试参数、无故障注入分支。Fake solver 当"事件录像机"（记录 reset/set_applied/solve 顺序——**顺序本身是被测行为**）。AtomicFreeze 测试用 `try_lock` 当探针证明互斥真实生效 + 双拍断言（"本拍旧、下拍新"）。

## 小结

1. TOCTOU 解法是 check+use 同临界区；慢活锁外；多锁全局定序。
2. 队列满了要"诚实地丢"：序号先分配，缺号+dropped 让丢失可观测。
3. 跨进程身份不能靠名字（PID 复用），内核对象（pidfd）才公证；跨线程生命周期不能赌时序，所有权（SharedPtr/join）才作数。

## 自测（含答案）

**Q1：sequence 分配挪到锁外会怎样？**
A：并发取重号——bag 里两个 seq=7，检查器 `sequence_gap_duplicate_or_regression` 判 recording 失败、`state_by_sequence` 后写覆盖；`first/last` 边界撕裂。序号是单调全序号，其唯一性是"缺号即丢"推断的前提，必须与队列操作同临界区。

**Q2：join 为什么绝不能在锁内？**
A：工作线程每发一条要 `lock(mutex_); ++emitted`，退出前还要最后一次拿锁——锁内 join 等于等待一个需要这把锁才能结束的线程：永久互等。join 属于"慢活"（可能 100ms+ 排空）。

**Q3：poll vs waitid(WNOWAIT)？**
A：waitid 隐含父进程语义、在内核登记"收割者"身份（WNOWAIT 一旦去掉就变偷偷收尸）；poll 纯只读、连"我在等你"都不留痕。与租约同理：**证据机制本身不能有副作用**；监管器的权限边界是只观察不干预。

# 模块 5：ROS 2 工程机制

对应代码：回调组布局、`mpc_node_main.cpp` 关机链、`fix_qos_relay.py`、launch 三层、rosbag2。

## 5.1 回调组 × 执行器

> 同一 MutuallyExclusive 组的回调无论多少线程都绝不并发；不同组之间可以并发（受线程数限制）。

项目布局（[mpc_node.cpp:447-452](../src/usv_mpc_cpp/src/mpc_node.cpp#L447-L452) + main:60 的 3 线程）：

| 组 | 成员 | 类型 | 为什么 |
|---|---|---|---|
| `io_cb_group_` | 五个传感器订阅 | **Reentrant** | odom/imu 彼此独立并行；控制卡死时观测不断流 |
| `control_cb_group_` | 控制定时器 | **MutuallyExclusive** | 防拍叠套——**solver capsule 单线程占有是硬约束**（acados 非线程安全） |
| `research_clock_group_` | /clock | MutuallyExclusive | 观测自身串行 |

组是粗粒度第一道防线，锁是细粒度第二道——只靠组不设防、或全 Reentrant 处处互斥，都是失衡。

## 5.2 QoS：不匹配的代价是静默零消息

关键规则：

```
订阅 Reliable + 发布 BestEffort → ✗ 完全不兼容，零消息、无报错
订阅 BestEffort + 发布 Reliable  → ✓ 降级为 best effort
```

**RTK 断流事故**（[deploy_records/20261009_rtk_ntrip_fix.md](../deploy_records/20261009_rtk_ntrip_fix.md)）：两层结构——修掉 CORS 账号过期（HTTP 401）后**依然没差分**（第一个问题掩盖第二个）；真凶是 MAVROS raw/fix(BestEffort) vs ntrip_client 订阅(Reliable) 不兼容，GGA 上不去、VRS 不发差分、无任何 QoS 报错。ntrip_client 未启用 `qos_overriding_options`，参数表**静默无效**。

解法：[fix_qos_relay.py](../src/usv_bringup/usv_bringup/fix_qos_relay.py)（38 行）——一个进程两端各用匹配对面的 QoS，把"不兼容"拆成两段"兼容"。

transient_local 正面用法：worker 能力信标（[solver_worker.cpp:27](../src/usv_research_safety_cpp/solver_worker.cpp#L27)）`.reliable().transient_local()`——监管器晚启动也能拿到最后一条。**排障口诀：节点都活着就是没数据 → 先 `ros2 topic info --verbose` 查两端 QoS。**

## 5.3 launch：两阶段模型

- **声明期**：`generate_launch_description()` 构建对象树，`LaunchConfiguration` 只是符号。
- **执行期**：`OpaqueFunction` 里 `.perform(context)` 才有真值——校验放这里。
- `ParameterValue(..., value_type=bool)`：CLI 来的参数全是字符串，不标类型 `as_bool()` 直接抛异常。

p0 入口校验四连（[p0_contract_recording.launch.py:17-42](../src/usv_bringup/launch/p0_contract_recording.launch.py#L17-L42)）：run_id 路径安全正则 / config_hash 64hex / **目录必须不存在**（lexists） / **两目录互不包含**——在 launch 层拦截比节点运行中崩溃便宜一个数量级。

隐藏参数坑：`controller_vehicle` 无 DeclareLaunchArgument（[vrx.launch.py:117-118](../src/usv_bringup/launch/vrx.launch.py#L117-L118)）——功能成立（include 传参不要求声明）但 `--show-args` 不显示。**launch 参数的"声明"是给人的文档，不是给机器的门禁**。

## 5.4 关机流水线

```
SIGINT → pre-shutdown callbacks（context 仍有效，还能 publish!）
       → executor spin 返回 → main 继续 → context 死
```

研究模式必须 `add_pre_shutdown_callback`（[mpc_node_main.cpp:53-58](../src/usv_mpc_cpp/src/mpc_node_main.cpp#L53-L58)）：`safe_shutdown` 最后一步等 logger 排空 1024 条并逐条 publish——用 `on_shutdown` 则 flush 时 context 半死、`publish_errors_++`、`normal_end=false`（数据被自己标记不完整）。非研究模式用更保守的 on_shutdown。

信号线程异常必须吞掉（lambda 里 try/catch）——逃逸即 std::terminate，没有优雅关机。

## 5.5 进程编排即方法学

p0 入口 `return [recorder, include]`：**recorder 先启动**（否则开头数据静默丢失——DDS 发现要几百 ms）；**控制器退出不联动杀 recorder**（logger 排空的尾巴要进 bag，`sigterm_timeout=15` 留足刷盘）——8 步 pilot 流程"先停控制器、验 summary、再停 recorder"的代码根源。

## 小结

1. 并发能力 = 组 × 线程；solver capsule 单占决定控制组必须互斥。
2. QoS 不匹配静默零；修不了第三方就中继拆两段；transient_local 是"晚到拿最后一条"配方。
3. launch 是两阶段的：校验放 OpaqueFunction；进程编排（谁先起、谁不许联动死、给谁留 flush 时间）本身是实验方法学。

## 自测（含答案）

**Q1：control 组改 Reentrant 会怎样？**
A：上拍 solve 阻塞时下拍回调可并行进入。state_lock 会让冻结段串行化（救场），但 `mpc_` 同一 capsule 被并发 solve——acados 非线程安全，真 UB；`research_cycle_`/`last_commanded_*_` 也被交叉写。控制组互斥不是风格，是 capsule 单占的硬约束（P1 拆进程是它的彻底版）。

**Q2：中继发布端 `create_publisher(topic, 10)` 的 QoS？ntrip 改 BestEffort 后中继还工作吗？**
A：KeepLast(10)+Reliable+Volatile。仍然工作（Reliable 发布向下兼容），只白付重传开销（1Hz 下趋近零）。真正的风险是有人把中继**订阅端**"优化"成 Reliable——当场重演事故；注释写死两端 QoS 的理由就是防好心优化。

# 模块 6：数据契约设计 —— 黑匣子怎么造

对应代码：8 个 .msg、`check_p0_contract.py`、`check_reference_prediction.py`、`research_config_sources.py`。

## 6.1 数据 ≠ 证据

**数据是"发生过的字节的堆"，证据是"能回答问题的字节的链"**。契约三层缺一不可：

```
① 消息本体（.msg 字段）  ② 生产纪律（发布端承诺）  ③ 验收合同（checker 断言）
```

**只有 ③ 存在时 ①② 才叫"承诺"**——否则是注释里的愿望。checker 自己也要被检查（177 项 pytest 测"它会怎么被骗"）。

## 6.2 身份块

每条消息自带：`schema_version / run_id / producer_instance_id(run+出生steady时刻) / baseline_id / config_hash / sequence / clock_epoch / steady_clock_domain(boot_id:steady_clock)`。

每个字段对应检查器一类离线拒绝：重启撞 sequence 被 producer_instance_id 区分；跨 boot 时间差被 domain 拦；跨纪元拼接被 epoch 拦。**身份不是自洽即可，还须与外部冻结的 run_context 一致**（防"全部伪造但内部自洽"）。

## 6.3 StateSnapshot：原子性的证明

承诺："六维完全来自同一条 ground-truth odom"。生产端从同一条 msg 抽六维；IMU 覆盖 r 时**打标签**（`state_kind: controller_mixed`，不隐藏）。无效样本照发但 `valid=false` + 有限占位 0 + quality_reason——宁可诚实的无效记录。

验收（[check_p0_contract.py:344-365](../../scripts/check_p0_contract.py#L344-L365)）：按 (stamp, frame, child) 从原始 odom 流找回那条 → **独立重建六维**（yaw 公式独立再写一遍，不复用生产代码）→ 逐分量 1e-5 比对。**验证代码复用被验证代码 = 没验证**。"Same body-frame twist, with no yaw rotation applied again" 注释钉住历史 bug（yaw=90° 时 twist 被二次旋转）。

## 6.4 五个永久 false

`AppliedControl` 尾部：`plant_acceptance_observed / force_measured / execution_atomicity_proven / exact_execution_timing_available / gp_labels_ready`。

**每个"不能声称的能力"在数据结构里占显式位置**。链式依赖：前四个 false（发布≠接受/无传感器/两话题无原子性/无执行时刻）共同导致第五个（GP 标签需要执行侧真相）。checker 执法：**必须为 false**——改成 true 骗通过直接判整份 bag 无效。科研语境下过度声称比错误更严重——错误可推翻，模糊声称污染所有下游结论。

## 6.5 AppliedControl 关键设计

- `event_semantics="publisher_command"` 自我限定——防三年后被解读为"物理执行事件"。
- **左右两路各自记录 clock 采样**——两路 publish 之间 clock 可回退，`channel_clock_epoch_mismatch` 拒绝联合区间。
- **部分发布 = 完整失败**：左成功右失败如实记录并 rethrow，`partial_or_failed_publication` 判失败——不支持任何联合区间。

## 6.6 配对窗边界

armed 跨度由**配对成功记录的 min/max 索引**事后归纳：跨度内未配对 = 失败；跨度外保留计数、不做声明（"no completeness claim for these"）。容差 1e-5N 是序列化往返容差。400ms 长保持测试的构造：所有域整体平移 +200ms——报告**通过**但 ledger 如实呈现 0.4s + long_hold **warning**。

**failure vs warning 的判据：违反合同 = failure；合同允许但值得注意 = warning。**

## 6.7 防伪造（负空间设计）

- `prediction_available=false` → 形状必须全零、数组必须为空（"不可用的预测不许带数组"）
- 失败/迟到解的 X/U **故意不复制**；standby 拍不产生 reference 事件（`reference_fabricated_for_no_solve`）

**契约不仅规定"该有什么"，还规定"不该有什么"**——后者更能暴露生成端 bug（生成了不该有的 = 代码走了不该走的路径）。

## 小结

1. 证据 = 数据 × 身份 × 独立验证；复用被验证代码的验证不算验证。
2. 能力边界写进数据结构，checker 把"必须为 false"当执法对象。
3. 诚实优先于整洁：部分发布算完整失败、end_unknown、窗口外不声明、失败解不带数组。

## 自测（含答案）

**Q1：同戳双 odom 一条吻合一条差 0.3m，checker 通过——合理吗？**
A：合理且本系统必须如此。同 (stamp,frame,child) 双条几乎只能是 DDS 重投递（相同字节，重建结果逐位同）——0.3m 差异意味着上游给不同数据打了同戳，是更上游的失信。风险可接受的根基：odom 是 VRX ground-truth（无 EKF 融合/重采样）。换实机 EKF 输出时须收紧为"全部吻合"——**契约严格度必须与数据源语义匹配**。

**Q2：换带 header 的消息能让 execution_atomicity_proven 变 true 吗？**
A：不能。原子性要证明的是**消费侧**（Gazebo 各自订阅两话题、各自回调、各自写物理引擎）的采样落在同一控制区间——header 只解决发布侧标注。缺的环节是 Gazebo 侧接收确认（plant ACK），这正是 `plant_acceptance_observed` 的含义：证明责任在执行端。

**Q3：同 boot 同 run 但节点重启，区间怎么断？**
A：序号连续性断它（重启后 seq 从 1 重来，302→1 不相邻）。两段各自形成合法区间直到各自 end_unknown。序号连续的本质：**"同一生产者不间断在线"的具体证明**——断档唯一可能原因是死亡/重启/丢消息，三种都使"相邻事件间的物理保持"失去意义。

# 模块 7：P1 监管器（三讲）

## 第一讲：架构动机、固定 tick、三线性化点

### 架构

```
p1_regulator (prepare/tick/Sink 三线程)          p1_solver_worker (单工作线程)
  ── /p1/solve_job (reliable, depth 1) ──────▶     独占一个 acados capsule
  ◀─ /p1/solve_candidate + /p1/worker_capability   失败即隔离不重启
  └─ 仅 execute 模式有物理发布者（当前硬编码关闭）
```

进程边界三收益：**求解阻塞不传染**（tick 照常决策）；**故障域隔离**（worker 崩 = pidfd 可见的进程死亡）；**capsule 单占成物理**（跨进程无共享内存）。**唯一决策者原则**：tick 线程是全系统唯一触碰物理发布者的执行流——每条命令可归因。

### 固定 tick

> 在 t_k 执行由上一周期验证好的 q_k；t_k+150ms 只原子提交候选；t_(k+1) 再核对后发布。

**发布不等任何求解**——求解慢只影响"下拍有没有新候选"。150ms = 15+80+40+15 设计值（非测量、非硬实时保证）。**不得提前发布**：离散模型假设每拍恰保持 dt=0.2s，提前 50ms 发则首段保持 250ms、预测全部错位——**命令时刻的精确性优先于提早**。

tick 九步（[regulator.cpp:255-307](../src/usv_research_safety_cpp/regulator.cpp#L255-L307)）：绝对节拍 → 调度纪元检查（clock 异常 → origin 重置 tick 归零）→ 跳拍检测 → pidfd+租约 → 暂停确认 → 看门狗 → 锁下快照 → take ticket → 决策 → 发布 → **睡过 150ms 才 cutoff**（执法时刻刻意的位置）。origin = 启动后 1 秒（给 DDS 发现/worker 握手留缓冲——第一拍就按完整纪律执行）。

### 三线性化点：ready → committed → taken

| 点 | 线程 | 时刻 | 语义 |
|---|---|---|---|
| ready | candidate 回调 | 任意（≤deadline） | "我有一个候选，目标 t_(k+1)" |
| committed | tick 尾部 | 过 150ms | "定稿这个" |
| taken | tick 头部 | 到 200ms | "用它决策"（一次性） |

为什么三刀：回调线程与 tick 线程解耦（决策关键路径无回调持有的锁）；committed 与 taken 之间的 50ms 是"定稿后、盖章前"的最后体检窗口。

`Admission`（[p1_admission.hpp:103-130](../src/usv_research_safety_cpp/p1_admission.hpp#L103-L130)）关键细节：

- **register 七拒绝码**：wrong_tick / version_mismatch / time_contract（deadline 必须==origin+150e6 这种等式也验）/ late / duplicate（64 深去重窗）/ cutoff_closed / ready_slot_full
- **"closing at equality is forbidden"**：cutoff 用严格大于——`now==deadline` 这一瞬的语义唯一属于注册方，消除"两个规则都想管边界"的竞态
- **take 里惰性补 cutoff** + `committed_->target < target` 丢弃（过期定稿不可补用——"不补拍"的 admission 层实现）
- Decision 消息记录全部六个时戳（planned/start/ready_commit/cutoff_commit/activation_commit/end）——**消息本身就是 profiler**

### 自测答案

1. schedule 重置会 `invalidate_locked()` 清掉 committed；即使没有 invalidate，残留槽只有 take 匹配 target 才被取出，发布只发生在 take 成功的拍——**占用即最坏后果，槽位设计的安全方向**。
2. 跳拍时循环尾 cutoff 立即返回但仍为 t_(k+1) 服务（关闭对象是 ready_ 里的票）；take 里的惰性 cutoff 幂等（`!ready_ → return false`）——**迟到执行的执法仍然是执法，只是对象已过期**。
3. 135° 判断依据（psi 与 ref 的偏差）是冻结在 Job 里的输入——判断应由拥有该输入的一方在具名时刻做出。worker 自判则决策不可复现（越权 + 不可归因）。**所有影响执行资格的判断必须可归因到具名时刻的具名输入——所以以数据（Job 字段）而非代码（worker 逻辑）存在。**

## 第二讲：拒绝原因码体系与决策序

### 四道墙

```
墙1 资格层 eligible()      "现在的世界还适合做决策吗"
墙2 候选层 candidate()     "这个候选本身可信吗"
墙3 激活层（锁下决策序）   "决策期间世界没变吗"
墙4 提交层（commit 复查）  "最后一刻还成立吗"
```

**每个码是一次被命名的事故**；码是数据不是日志（Decision.reason 进 bag——拒绝码分布是系统健康度的 X 光片；F5 run 的 21/22 anchor_mismatch 就是这样发现的）。

### 墙 1 精选

- 复用 `input_eligibility`（与 B 逐字一致——影子对比的前提）
- **混源双税** `mixed_source_age_or_skew`：接收年龄税 + 物理偏斜税（|imu_stamp−odom_stamp|）——原子性免的税，混合要补交
- **两轴四象限**（`state_source_check`）：`receive_stale`（回调慢，steady 域）vs `sim_lag`（数据出生就旧，sim 域）——**两种旧由不同故障造成、需要不同修复**；`sim_future` 容忍仅 20ms（未来的数据比过去的更可疑）
- `rtf_unaligned`：外推 `current_sim = clock_sim + elapsed` 假设 RTF=1——根基坏了一切免谈
- `unknown_anchor`：不知道上拍执行了什么时，新命令无法验证为物理合法

### 墙 2 精选（检查链越便宜越前——顺序是诊断协议的一部分）

- `foreign`：schema/run/boot/contract_hash/nominal_hash/worker_instance 六串全等——防配置漂移不是防黑客
- `shape_or_time_contract`：数值关系也是合同（deadline==origin+150e6 精确等式）
- `job_echo_mismatch`：候选完整回显 Job 与原件逐字段比——**输入的完整性靠输出的回显证明**
- `first_control_mismatch`(1e-8)/`prediction_initial_mismatch`(1e-7)：**消息内部字段互为校验和**

### 墙 3+4：检查做两遍

锁外（快照）+ 锁下（实时状态）——**把"检查时刻"与"发布时刻"的距离压进锁临界区**（TOCTOU 教训的终极形态）。精选码：

- `activation_input_changed_during_validation`：快照 seq ≠ 实时 seq → 验证期间来了新状态（用序号侦测变化，比逐值便宜且不漏）
- `state_check`：激活容差 [0.25, 0.25, 0.15, 0.3, 0.2, 0.15]——名义模型与实际世界的分歧预算
- `command_check`：`|u−a.n| ≤ rho·Δt + 1e-9`——合法命令都落在从锚点出发斜率 ±80N/s 的锥内
- `target_sim_mismatch`：prepare 时外推的 target_sim vs 提交时实测外推——20ms slack = RTF∈[0.95,1.05] 一拍内最大累计偏差（0.05×200ms=10ms）的一倍余量

### 版本五元组

`Version {task, model, config, schedule, epoch}`：task=path/profile 指纹变化；**model/config 是为 GP 在线切换预留的挂点**（递增 model → 旧候选自动 version_mismatch 失效）；schedule/epoch=时间轴断裂（origin 重置）。**混版从概念变成可判定的全等检查**。schedule 与 epoch 总是同增仍是两个字段——模型切换不该重置节拍（物理时间连续），epoch 变化必须重置（时间轴断了）——**语义正交，字段必须分开，否则两个决策互相绑架**。

### 自测答案

1. echo 比对挪最前会污染码分布——所有便宜可判的故障被记账成昂贵检查的名字。诊断信息要求"最能解释拒绝的那一层先开口"。
2. fallback 输出**不需要再过 command_check**：`copysign(max(0,|a.n|−rho·Δt))` 相对锚点变化恰为 rho·Δt 或 0——**锥的内点构造**，且与检查用同一份数据。数学证明替代运行时检查的少数场合；引入新输入时须重新论证。
3. 见上文版本五元组——model 切换不重置节拍、epoch 必须重置。

## 第三讲：影子模式、worker 纪律、契约即代码

### 影子模式：逼真性靠锚定

监管器无物理发布者，但决策依赖"上拍实际执行了什么"——**锚定 legacy B 的 F5 AppliedControl 流**（[regulator.cpp:187-199](../src/usv_research_safety_cpp/regulator.cpp#L187-L199)）：

五道门：身份五重验证（含 **baseline_id 必须是 F5 冻结基线**——数据合同按版本成立；map_scale==1）→ 生产者不许换人（B 重启即锚点作废）→ 纪元一致 → 序号严格连续 → 逐通道接收。断档处理统一"清空重来"（宁要几分钟 unknown_anchor，不要带断档历史做衰减）。

**模式差异压缩到两个 if**（execute 才建发布者、shadow 才订锚点），决策序全共享——影子期的决策流证据**直接适用于** execute 期（同一段代码）。

### worker 纪律

1. **单槽顶替**（pending_replaced），不排队——任务是时限商品，积压全是废票
2. **job_id 严格递增**——乱序到达的旧任务无论多正确都是过期答案
3. **quarantine**：native 失败 → `fatal_=true` 本 run 永久退出，`"policy":"quarantine_this_run_no_restart"`。三层理由：失败有相关性（重启面对同样输入大概率再败）；worker 无法区分"输入病态"与"自身损坏"（区分不了就当后者）；**pidfd 让死亡成为信号**。对照 crash→respawn：那是可用性哲学，P1 要可信性——**宁可没有解，不要可疑的解**；失败政策写进契约本身
4. **受控屏障故意放 native 路径**：模拟"acados 永久挂死"——worker 不自救（native 内加超时违反 capsule 单占），**卡死就卡死，让外部 supervisor 杀**

### 契约即代码（p1_full_contract.hpp）

`load_contract`：读文件(≤64KB) → SHA-256 与参数 hash 比对 → 解析校验——**内容、身份、结构三者同时成立**。

三层校验：**重复 JSON 键拒绝**（解析器的后者覆盖前者=幻觉字段）；**bool 不许冒充 int**（`strict_i64`——C++ 契约校验从第一天防了 10-13 审查在 Python 侧发现的漏洞）；**数值钉死**（除资源字段外与内置基准逐值相等——N=20/T=200ms/deadline=150ms/±25N/rho=80...你能改的只有缓存大小）。

三档 profile：Diagnostic（当前，shadow）→ PreFreeze（pending 校准项冻结）→ Frozen（证据哈希+禁故障注入，才许 execute）。**每档能做什么被数据限定，升档是数据变化不是人拍板**。

**最硬的墙**：`physical_execute_release_enabled = false` 是 **constexpr**——任何配置打不开 execute，必须改源码重编译（二进制哈希变化被证据链看见）。**用摩擦力当安全机制**；报错信息写明 "disabled until B5/M4"。**数据说你可以（资格）≠ 代码让你可以（授权）——授权高于资格。**

### 资源上界（p1_resources.hpp）

CDR 字节模型：对齐填充 + 4 字节长度前缀（**字符串终止 NUL 计入**）+ 序列计数前缀；连 FastRTPS "空序列也按元素对齐"的怪癖都建模（**与真实实现一致而非与规范理想一致**）。`append_job` 按消息定义顺序过模型，静态断言钉死 job 6460B / candidate 8204B。检查在每个接收回调第一行——**先于一切业务逻辑**。诚实边界："These bounds protect application work after a typed callback begins"——中间件已分配的内存不归它管。

### 收束：P1 在研究路线里的位置

| 研究概念 | P1 工程形态 |
|---|---|
| 执行一致性 | 版本五元组 + 四道墙 + 三线性化点 |
| 有效性管理 | deadline + 年龄门 + 激活容差 + target_sim_slack |
| 模型切换挂点 | `Version.model` + worker 独占 capsule |
| 认证备份 | **P2 的活**（P1 只交付 fallback） |
| 安全证明边界 | 影子模式 + 五个 false + execute 硬编码关闭 |

### 自测答案

1. legacy B 改 `vrx_thrust_scale=0.9` → 每条 AppliedControl 被**静默**丢弃（门 1 无 event 日志）→ 锚点永远 unknown → 100% fallback 空转。不崩溃、无配置告警——**锚定契约是影子的隐性前提，失效无专门信号**（review 建议加启动声明的原因）。
2. quarantine 前候选已 publish：regulator 墙 2 的 `solver_failed` 保证它不被接受，只作为带码记录进日志——**失败现场（job 回显/backend_ms/原因）进 bag**，不发则只剩"worker 忽然 silent"。失败也是证据，前提是如实标注。
3. 升 Frozen 不需改屏障代码：`TickBarrier(ms, mode, fault_enabled)` 在 `fault_injection_enabled=false` 时任何非零参数构造即抛——**注入能力被数据自动关闭**。代码保留可能性、契约决定可用性——与 execute 的 constexpr 方向相反、原则相同：**危险能力的开关放在最难悄悄改动的那一层**。

# 模块 8：RL 部署链 —— 一次真实事故的工程闭环

对应代码：`export_policy.py`、`rl_policy_node.py`、两个测试文件。

## 8.1 PPO 确定性部署 + VecNormalize

训练学随机策略（高斯 μ(s)+采样，为了探索）；部署用 μ(s)（确定性——可复现可审计）。

**VecNormalize 陷阱**：训练时观测先过在线标准化 `(obs−μ)/√(σ²+ε)`，网络学的是标准化空间的映射。只导权重忘统计量 → 部署喂原始观测 → 输出垃圾且**不一定像垃圾**（平滑函数给一堆看起来正常的数）。解法：**折叠进图**（[export_policy.py:84-102](../../../usv_rl/usv_rl/export_policy.py#L84-L102)）：

```python
forward: norm = (obs-mean)/sqrt(var+eps) → clamp(±10) → net → clamp(±1)*thrust_scale_n
```

统计量 `register_buffer` 进图——**部署单元 = 单个文件**，且 `vn.training=False` 冻结（防对拍时统计漂移）。

## 8.2 事故复盘：±1 N 的船

v5 训练改了动作空间归一化 [-1,1]，旧导出的"action_space 反缩放"变成恒等变换——**网络输出 [-1,1] 直接发给 N 量程 ±25 的话题**。VRX 实测：最大推力 ±1N、船 0.267 m/s 爬行——不是不动，是极慢地动，看起来像"训练得差"，无任何报错指向单位。

**四道防线为何全漏**：训练闭环自洽（环境 step 自己乘 25）；导出验证用 actor 自己当 oracle（**被验者=验证者，双双通过**）；部署无单位校验；人眼看数字都在合法范围。根因一句话：**单位是接口语义，而接口语义没有任何载体**——训练/导出/部署三方对"输出的物理含义"没有共同声明。

## 8.3 修复三件套

1. **图内缩放**：`--thrust-scale-n` 必填且只接受 25.0——要改推力上限是全链路同步变更，不是导出参数调整。
2. **独立 oracle**：`_verify` 用 SB3 原生 API（`vn.normalize_obs + model.predict`）作参考，与导出图**零共享实现**；语料 = 64 合成（固定种子）+ 可选真实观测 .npy；容差 1e-3N。**验证的独立性高于覆盖——验证自欺比不验证更危险（它给你继续错的信心）**。
3. **契约式发布**：onnx + manifest 成对；manifest 含声明（单位/维数/顺序）、溯源（三个 SHA+源路径）、证据（对拍记录/命令行/环境版本）；图内 `usv.*` 元数据双通道。发布协议：mkstemp → 写 → 验 → **os.link 原子发布**（目标不存在才成功）、失败撤销、**绝不覆盖**——部署模型是证据链一环，覆盖后"上次部署的是什么"永远说不清。

## 8.4 部署侧硬校验

`load_policy_contract`（[rl_policy_node.py:54-90](../src/usv_rl_ros/usv_rl_ros/rl_policy_node.py#L54-L90)）四道：manifest 存在可读（裸 onnx 拒）→ 合同逐字段**类型+值**全等（bool 冒充 int 也防）→ **双向锁**（manifest 25N ↔ 节点 t_max 25）→ **字节级 SHA256**。`validate_policy_session` 再验真实 ORT 接口 + 图内元数据与 manifest 互证。

失败行为：**不崩溃不退出，永远 STANDBY 零推力**（reason=model_contract_invalid）。为什么苟活不自杀：**VRX 里推力会被 Gazebo 锁存——死节点留下的最后命令永续执行**。与 P1 worker 的 quarantine 对照：**有没有上层监管者，决定失败时该自杀还是该苟活**——无人监管的节点，自己就是自己的监管者。

## 8.5 NaN 纵深与异常盾

NaN 的恶毒：`np.clip(NaN)` 返回 NaN（clip 拦不住），一路进物理引擎。**四道门**：odom 样本（四元数范数+isfinite）→ 状态 isfinite → 观测 isfinite → **推理输出 isfinite**（最后一道必须存在：float32 溢出/下溢可以让干净输入算出脏输出；且门 3 必要——中间变换如三角/插值能自己造 Inf，如路径 pose 混入 Inf 纵坐标 → `np.interp` 得 Inf，**状态干净、观测脏**）。

**异常盾**（[:315-328](../src/usv_rl_ros/usv_rl_ros/rl_policy_node.py#L315-L328)）：定时器回调异常逃进 rclpy.spin → 节点死亡 → 推力锁存 = 失控船。模式：捕获一切 → 零推力 → 定时器活着下拍重试。配套 `_fin()` 清洗（NaN 不进 JSON）、删除 `schedule_rebase_m=2.0` 死赋值（参数读进来立刻被覆盖=配置永远不生效）。

**路径指纹**（[:246-252](../src/usv_rl_ros/usv_rl_ros/rl_policy_node.py#L246-L252)）：规划器每秒重发同一路径（戳会变）——用**几何指纹**（点数+首末点坐标取整毫米）区分"重发"与"真·新任务"，任务时钟不因重发归零。**用内容而非到达事件定义"新"**。

## 自测（含答案）

1. **运行中替换 onnx 算漏洞吗？** 不算——威胁模型划对了。加载时校验防**部署事故**（拿错文件/传输损坏/配错 manifest——发生在"导出机→部署机"链路）；运行中替换需要文件系统写权限，此时攻击者也能换节点代码本身，校验 onnx 无意义——**每层防它那层的威胁，下层托底的上层不重复**（文件系统完整性由 OS/部署流程担保）。
2. **门 3 场景**：`_path_cb` 只查 n≥2 不查有限性——路径某 pose 纵坐标 Inf → `np.hypot` → `s` 含 Inf → `np.interp` → 观测含 Inf。**中间计算不是恒等映射，每道门检查的是它后面那个计算的输入**。（也是 `_path_cb` 值得补的检查——B 节点有 `invalid_path`，RL 侧靠门 3 兜底。）
3. **训练侧 assert 能更早暴露吗？** 不能——assert 验证的是"我这一侧自洽"，而单位错位的定义就是"**每侧各自自洽、合起来错位**"。接口语义不存在于任何一侧，只存在于两侧之间——**只有"中间物"（manifest）能表达接口**，所以合同必须三方共持。

# 模块 9（终章）：验证方法学

对应代码：`collect_repair_baseline.py`、五个真实基线、`.pre_*` 备份链、资格表。

## 9.1 基线冻结：回答 Git 答不了的问题

**"2026-10-05 13:47 那次 pilot 运行的是什么代码？"**——运行态 ≠ 任何 Git 对象（dirty 工作区 + install 产物 + 独立模型文件）。

五层档案（[collect_repair_baseline.py:283-378](../../scripts/collect_repair_baseline.py#L283-L378)）：

```
① 身份：git head/branch/status/diff 全文          ② 源码：白名单快照（146 项）
   —— EXCLUDED_NAMES 排凭据 + secret/token 正则纵深  ③ 安装：实际 install 产物（177 项，prefix 必须指向本 workspace）
⑤ 完整性：采集后重扫三组清单+git 复核               ④ 模型：5 项
```

第 ⑤ 步是精髓：**采集中源文件变了 → `*_changed_during_collection` → 冻结失败**（防新旧混合体）。测试用**真实磁盘写入**注入变异（`after_copy` 变异缝——测试基建不污染生产路径）。

## 9.2 哈希链：锚定源头而非声明

```
p0_nominal_f3.yaml ──canonical 序列化──▶ nominal_effective.yaml (SHA=78d7133f…)
   ──写入契约──▶ p1_full_contract.hpp nominal_hash ──回显──▶ SolveJob/SolveCandidate
```

**验证方法 = 从源头重算**（我重算过，逐字符一致 + 19 水动力参数零差异）——不是"下游互相对账"（那只证明下游一致）。C3.4 实验证明递归伪造免疫：把 storage 里 120 条消息的哈希全部同步改假值，独立预像重算当场揭穿——**攻击者能改所有声明，改不了哈希函数的数学**。

这是同一原则第四次出现（原子重建/双计时/SB3 oracle/哈希重算）：**验证 = 用独立路径重现被验证的事实**。

## 9.3 F1–F5 与归因粒度

```
F1 三修复原样冻结(时间零点) → F2 数据契约 → F3 四元数门禁+三实现对拍(291例,差≤8.9e-16)
→ F4 nominal/plant 分离+单因素 probe → F5 原子冻结
```

**归因粒度决定结论强度**：一个大提交的世界里"机制 X 有效"无法排除 Y 的作用；F4 的单因素 probe（只改 plant.mass，其余哈希冻结）能说"质量失配单独造成此差异"。**单变量保证不靠纪律（"记得没改别的"），靠哈希（别的变了冻结就失败）**。

`.pre_*` 备份是**改前帧**（证明"从什么变成什么"），基线是**改后帧**——每步演进有前后两帧。验证方法：`diff <(sed 's/[[:space:]]//g' A) <(sed 's/[[:space:]]//g' B)` 去空白滤格式噪声，只看语义。代价：10 个备份未 ignore 有误提交风险——证据文化的维护成本。

## 9.4 资格 vs 组件

C3.4 资格表：组件 175+143+6+3 通过 **∧** strict/阶段全部 false——**不矛盾，是两把尺子**。组件=砖（给定版本输入前提下某链路验证过）；资格=楼（全部必要条件满足才许进入后续动作）。**组件数不累加成资格**；false 不是否定而是"差什么"的清单。防的心理陷阱：**完成焦虑驱动的资格膨胀**——代码层的化身就是 constexpr（**文档可以说服，代码不能**）。

## 9.5 统计纪律

1. **零事故 ≠ 概率保证**：n 次零事故的单侧 95% 上界 `1−0.05^(1/n)`（n=100 → 2.95%）——只排除"事故率高于 3%"的世界。
2. **P99 ≠ 硬实时**：筛选指标，硬实时要 WCET 证明；最大值与 P99 并列报告。
3. **阈值先注册**：防事后择优（p-hacking 工程版）；"积分误差大于容差应改方法重新冻结，不能调容差抹去违规"——**数字改不动事实**。

## 9.6 课程合流：九模块同一原则的九次变奏

```
模块2 时间域不混算    —— 声称的耗时只在证据支持的域内成立
模块3 fail-closed     —— 无法验证的时刻按失败处理
模块4 诚实地丢        —— 丢失可观测优于完美伪造
```

**贯穿始终的一课**：这个项目最独特的产出不是监管器本身，是它把"诚实"工程化的方式——每个"不能声称"都有字段、每个拒绝都有名字、每个版本都有哈希、每个资格都有清单。机器不会撒谎，但人会说"差不多"——**这套系统的全部精密，都在消灭"差不多"**。
