## 0. 一页结论

**这是一个做得不错的工程原型，不是可发表的研究进展。**

三条支撑判断：

1. **头条性能结论建立在未调参的基线上。** LOS 基线（`los_controller.py` 的 6 个增益）自项目第一个 commit 起从未调优。评审者实测：只把 `lookahead_m` 从 2.5 改为 5.0，LOS 就在**横向精度和能耗上同时超过 PPO**（3 个种子，配对 t = 3.94~7.76）。因此 README 中"精度换能耗的权衡"不是权衡，而是被支配。
2. **成功率指标失去区分度。** 成功判据先于违规判据检查，且训练期关闭提前终止。评审者构造的"直线冲向终点"策略拿到 **96% 成功率**，期间最大横向偏离 **35.9 m**。PPO 与 LOS 都是 100%，该指标无法区分任何东西。
3. **与 MPC 的对比其实存在，且 PPO 落后。** 仓库中有一对**字节相同航点文件**（md5 `5aa742a5e391eaa704ee46c704b73049`）的 VRX 运行：方案B（NMPC）CTE 均值 **0.1007 m**、行进 58.02 m；方案C（PPO）CTE **0.1474 m**、行进 42.08 m。这对数据从未被分析或引用过。

同时必须说明：**工程链条本身是扎实的**——ONNX 契约式导出含独立 oracle 对拍、manifest 哈希硬绑定、训练与部署共用观测构造单一真源、多条失效保护路径。问题不在实现质量，在于**评估设计和研究设计**。

**状态**：该研究线自 **2026-10-03 起冻结**。`.sgh-research/experiments/` 中方案A 有 100+ 个实验目录（最新 2026-10-26），方案C 仅 2 个（均为 2026-10-03）。按 `docs/USV_reorg_plan_v5.md:168` 的明确设计目标，Pi5/Orin 分支**看不到** `usv_rl`——方案C 目前是纯仿真的研究线，无上船路径（此为设计选择，非疏漏）。

### 2.2 奖励设计

实现（`envs/usv_tracking_env.py:330-342`）：

```
cost   = q_x·dx² + q_y·dy² + q_pos_spatial·e_pos_sp²
       + q_psi·e_ψ² + q_u·(u-u_ref)² + q_v·v² + q_r·(r-r_ref)²
       + r_thrust·ΣT² + r_dthrust·ΣΔT²
reward = -0.2·cost + 15·Δs_prog  (+ 成功 +10)
```

权重与 MPC **逐字相同**：`Q=[20,20,50,8,1,8]`、`R=[0.05,0.05]`、`Rd=[0.2,0.2]`，直接抄自 `mpc_params.yaml:27-29`【代码核对】。

但必须区分"系数相同"和"目标相同"：

| 差异 | 说明 |
|---|---|
| 新增空间项 | `q_pos_spatial=100 · e_pos_sp²`，MPC 无此项 |
| 新增进度项 | `15·Δs`，**未乘 reward_scale**，MPC 无此项 |
| 缺终端代价 | MPC 有 `Qf_scale=8.0`，RL 用 ±10 标量替代 |
| 缩放不同 | MPC 阶段代价乘 `dt`，RL 乘 `reward_scale=0.2` |
| 目标泛函不同 | MPC 是有限时域无折扣代价；PPO 是折扣（γ=0.99）+ 奖励归一化 |

**结论**：README 中"RL 与 MPC 优化同一个目标，对比才公平"这句话**不成立**。评审者实测（附录 B-4）：按**纯 MPC 阶段代价**衡量，PPO 8.90/步，LOS 默认 9.69/步，而调参后的 LOS 只有 **4.13/步**。

### 2.3 五轮迭代史 —— 真实，且有时间戳佐证

README 记载的五轮 reward hacking 不是事后编故事。四轮修复各有独立 commit，且**提交时间与训练产物目录时间严格交替**：

|---|---|---|---|
| （骨架） | — | `e5d9c53` 训练侧骨架 | — |
| v1 | `rl_models/v1` 01:10:48 | `0590ac1` rebase + 终端奖惩 | 01:21 |
| v2 | `rl_models/v2` 01:57:57 | `d1b3408` w_progress 0.5→15 | 02:02 |
| v3 | `rl_models/v3` 02:39:33 | `4d69b69` 取消提前终止 + 动作归一化 | 02:57 |
| v4 | `rl_models/v4` 03:35:52 | `f256eb4` 空间项权重 100 | 03:56 |

**这是该叙事最强的可用佐证**：每个修复都落在它所回应的那次训练之后几分钟。代价是它也界定了规模——**五轮迭代是一夜之间的调试循环，不是研究战役**。

各轮的实际症状（均有曲线或 commit 支撑）：

### 2.5 导出与部署契约 —— 全项目做得最好的部分

**ONNX 图结构**（【亲测：解析实际产物】）：

```
obs(43) → Sub(obs_mean) → Div(sqrt(var+eps)) → Clip(±10)
        → Gemm/Tanh ×3 (MLP) → Clip(±1) → Mul(25.0) → thrust(2)
```

- 内嵌 `obs_mean` 与 `vecnormalize.pkl` 的 `obs_rms.mean` **差为 0.0**；`Div` 常数与 `sqrt(var+eps)` 差 1.19e-7
- 输出单位：牛顿，范围 ±25 N
- 独立 oracle 对拍（`VecNormalize.normalize_obs` + `SB3.predict(deterministic=True)`，再显式 ×25，**不读 actor 内部缓冲**）：最大误差 **1.907e-5 N**，容差 1e-3
- 硬编码 golden 用例：归一化动作 `[0.5,-0.5]` → 图输出 `[12.5,-12.5] N`

**哈希绑定**（【亲测】）：


**部署侧**（`rl_policy_node.py:54-95, 98-130`）：
- 校验 manifest 字段类型/取值（`contract_version`、`output_unit=="N"`、维度、`thrust_scale_n==25.0`、物理上下限）

## 3. 头条结果及其有效性

### 3.1 数字本身是真的、可精确复现

| 指标 | LOS 基线 | PPO v5 (s4_dr) |
|---|---|---|
| 成功率 | 100% | 100% |
| 横向误差 RMS | 0.404 m | 0.312 m |
| 横向误差 max | 1.172 m | 1.056 m |
| 航向误差 RMS | 25.8° | 16.1° |
| 能耗 | 2416.5 N²·s | 7338.5 N²·s |
| 控制平滑 | 114.7 N/ep | 1797.1 N/ep |

【亲测】重跑两个官方命令，结果与 `docs/report_assets/eval_{los,ppo_v5}_50eps.txt` **逐位一致**。因此 `.txt` 是 `evaluate.py` 真实产出，不是手抄。

**协议本身是公平的**（就种子/路径/DR 而言）：
- 两个分支默认 `seed=9999`（`evaluate.py:107`）
- 四个 DR 字段对两者**无条件置 0**（`evaluate.py:113-116`）
- 【复核】逐 episode 路径指纹比对：**50/50 完全相同**
- 配对统计稳健：seed 9999 下 PPO 在 41/50 episode 更好，配对 t=6.08；跨 5 个种子 t=6.6~9.0

### 3.2 但基线是稻草人 —— 这是决定性问题

`LosController` 的构造函数默认值（`baselines/los_controller.py:25-27`）：

```python
lookahead_m: float = 2.5
k_psi: float = 0.8
r_d_max: float = 0.35
```

`evaluate.py:120-126` 以 `LosController()` **无参**实例化。仓库中**没有任何调参记录、扫描日志或预注册**。

【亲测】只改 `lookahead_m = 5.0`，同一 50 条路径、同种子、DR 关：

| seed | LOS(默认 2.5) | LOS(调至 5.0) | PPO v5 | 配对 t (PPO−LOS调参) |
|---|---|---|---|---|
| 9999 | 0.382 m | **0.216 m** | 0.299 m | **+7.76**（PPO 更差） |
| 4242 | 0.424 m | **0.264 m** | 0.321 m | **+3.94** |
| 2024 | 0.414 m | **0.249 m** | 0.295 m | **+4.12** |

能耗同向：

| | LOS 默认 | LOS 调参 | PPO |
|---|---|---|---|
| 能耗 N²·s | ~2400 | **~2250** | ~7400 |

【复核】验证 agent 用 4 个**全新留出种子**（31337 / 424242 / 8080 / 271828）独立验证：LOS 0.246~0.268 vs PPO 0.313~0.335，配对 t = −4.6~−6.0，LOS 在 **72~84% 的配对 episode** 上更好；连 PPO 课程专门训练过的 **zigzag** 路径也输（LOS 0.222 vs PPO 0.251）。粗网格在 seed 9999 达 0.221 m、成功率仍 100%。

**关键点**：调参没有代价——成功率不变、能耗下降。这**不是权衡，是严格改进**。因此：

- ❌ "PPO 在横向精度上优于基线" —— **不成立**
- ❌ "精度换能耗的权衡" —— 不是权衡，PPO 在两个轴上都更差
- ⚠️ 唯一幸存优势：**航向误差 16.1° vs 17.9°（−10%）**，不是宣称的 −38%

另有两处结构性偏向 PPO：
- PPO 观测含 8 个前瞻点（最远 4.0 m），LOS 固定 2.5 m
- `e_ct` 正是 PPO 奖励中权重 100 的空间项所优化的量，而 LOS 从不优化它

### 3.3 成功率指标失去区分度

`_check_done()`（`envs/usv_tracking_env.py:344-365`）的顺序：

```python
if self.traveled_s >= ref.total_length - self.path_resolution * 1.5:
    return True, False, "success"      # ← 先判成功
...
if reason and self.early_termination:  # ← 违规判死，但 env.yaml 里是 False
    return True, False, reason
```

加上 `_update_progress()` 用 40 点（20 m）的单调最近点窗口，成功可以在不贴线的情况下达成。

【亲测】构造一个"只看终点、全速直冲"的策略（`/tmp` 下临时脚本）：

```
BEELINE 策略：成功率 48/50 = 96%
  每 episode 最大 |e_ct|：均值 19.63 m，最大 35.90 m
```

**96% 成功率、最大偏离 35.9 m。** 因此 v5 与 LOS 双双 100% 的对比毫无信息量——该指标无法区分"贴线跟踪"和"抄近路"。

### 3.4 与 MPC 的对比：数据已存在，且 PPO 落后

仓库中有一对**字节相同航点文件**的运行（md5 `5aa742a5e391eaa704ee46c704b73049`，起点同为 `(-532.000, 162.000)`）：

| | **方案B（NMPC / acados）** | **方案C（PPO v5）** |
|---|---|---|
| 证据路径 | `.sgh-research/experiments/nmpc_timeout_fix_20261003/results/baseline_active/` | `.../v5_scaling_fix_20261003/results/new_physical_n/` |
| 运行命令 | `vrx_baseline.launch.py scheme:=B` | `vrx.launch.py scheme:=C` |
| ACTIVE 帧 | 235 | 244 |
| **CTE 均值** | **0.1007 m**（n=2496，max 0.1207） | **0.1474 m**（n=2394，max 0.2032） |
| **行进距离** | **58.02 m** | 42.08 m（未走完 70 m） |
| 时长 | 56.72 s | 56.71 s |
| 求解/推理 | 0.1961 ms（acados backend） | 0.1296 ms（ORT） |

**MPC 的横向误差低 32%，且走得远得多。**

这对数据不能直接当严格 head-to-head（构建版本不同、PPO 未完成路径），但它是项目里**最便宜、最该先分析**的数据点，却从未被引用。任何"PPO vs MPC 谁更好"的结论都应以它为起点。

### 3.5 延迟宣称差 660 倍

PPT/教程称"RL 推理 0.03 ms，为 MPC 方案的千分之一量级"。

同机实测：

```
MPC acados backend 平均  0.1961 ms
PPO ONNX 推理 平均       0.1296 ms
比值                     1.51×        （宣称 1000×）
```

"百毫秒级"属于**方案A**（CasADi 运动学，85~128 ms），而被 PPT 点为"对比基准"的是方案B。**两者不是同一个控制器。**

另外，`0.03 ms` 这个数字在仓库中**没有任何产物文件支撑**；VRX 实测的 `infer_ms` 均值是 0.1296 ms（含节点内调用开销）。

## 4. 缺陷与可利用通道目录

按严重度排序。每项给出症状、根因、证据、复现方法、影响。

### D1 · LOS 基线未调参（**推翻核心结论**）

- **文件**：`usv_rl/baselines/los_controller.py:25-27`；`usv_rl/evaluate.py:120-126`
- **证据**：§3.2 【亲测 + 复核】
- **影响**：头条性能结论反转

### D2 · 成功判据可被抄袭满足（**指标失效**）

- **文件**：`envs/usv_tracking_env.py:344-365`（先判成功后判违规）、`:239-247`（20 m 进度窗口）
- **证据**：beeline 96% / 35.9 m 【亲测】
- **影响**：成功率零区分度；评估与训练都可能奖励"抄近路"

### D3 · 进度窗口捷径通道仍开着（v4 实际用过）

- **机制**：`_update_progress` 一次向前搜 40 点 = 20 m；`w_progress=15` **不乘 reward_scale**；空间项封顶只罚 `0.2×100×2² = 80`
- **算术**：单步可claim `20.16 m → +302.37`，对冲 −80 → **净 +222**
- **盈亏平衡点**：`80 / 15 = 5.33 m`
- **证据**：【亲测】注入式探针得 `+302.37 / −80.0`；【复核】v4 策略实测单步 `ds_prog=20.06 m`、离路径 9~13 m，拿 **+174 奖励**
- **现状**：v5 未利用（2734 步内最大 `ds_prog=0.540 m`），但**通道未关闭**

### D4 · `step()` 返回的观测里 `prev_thrust` 是旧的（**训练/部署语义错位**）

- **文件**：`envs/usv_tracking_env.py:227`（`obs = self._get_obs()`）早于 `:232`（`self.prev_thrust = applied`）
- **证据**：【亲测】

```
reset obs[-2:]  = [0, 0]
step1 applied   = [16, 16]
step1 obs[-2:]  = [0, 0]     ← 下一步状态观测报告的历史推力
env.prev_thrust = [16, 16]
_get_obs() 现在 = [16, 16]
```

- **影响**：策略看到的执行器记忆比实际晚一拍。ROS 节点是"先发布再存值"，语义又不同；且**所有零推力降级路径都不清 `prev_thrust`**，下一拍 ACTIVE 观测会报告上一次 ACTIVE 的推力
- **状态**：2026-10-03 的审查报告已指出，**至今未修**；`test_obs_equivalence.py` 只在 `step` 后手动调 `_get_obs()`，覆盖不到

### D5 · 奖励在 2~3 m 外梯度归零（**学习信号饱和**）

- **机制**：`schedule_pos_cap=3.0`、`spatial_pos_cap=2.0` 都是硬封顶
- **证据**：【亲测】

```
偏 1.5 m  reward = -55.109
偏 2.0 m  reward = -97.109
偏 3.0 m  reward = -117.109
偏 5.0 m  reward = -117.109   ← 与 3 m 完全相同
偏 10.0 m reward = -117.109   ← 与 3 m 完全相同
```

- **影响**：船一旦偏出 2~3 m，**朝向路径的梯度恒为 0**；这正是 v4 学会"直线冲线"的机制温床

### D6 · 安全门只验自洽性，不验图语义（**单位 bug 可复现**）

- **机制**：`load_policy_contract` 校验 manifest 字段 + ONNX SHA256 + ORT 张量签名，但 manifest 是**不可信输入**——哈希只证明自洽，不证明单位语义。元数据检查写成 `if name in metadata`，即**可选**。
- **证据**：【亲测】把已知有 bug 的 `policy.onnx`（输出 `[-1,1]`）复制成部署文件名、手工写一个字段齐全的 manifest（哈希按新文件算），`load_policy_contract` + `validate_policy_session` **全部放行**：

```
!! FORGED manifest on OLD [-1,1] graph was ACCEPTED by the safety gate
   节点会当作牛顿发布：[-0.04447156  0.7065463]  （最大 |T| 只能到 1.0 N）
```

- **同一路径的另两种变体**（【复核】）：把图的 `Mul` 常数从 25.0 改成 1.0 并刷新哈希 → 通过；删掉全部 `usv.*` 元数据并刷新哈希 → 通过
- **影响**：10-03 那个事故的复现路径仍在。建议加"饱和探针断言输出范围" + 强制元数据必须存在 + 图内无可达路径通向归一化输出

### D7 · 代码默认值 ≠ `env.yaml`，测试测的是另一个 MDP

| 参数 | 代码默认 | env.yaml |
|---|---|---|
| `early_termination` | `True` | `False` |
| `max_steps` | `300` | `450` |
| `w_progress` | `0.5` | `15.0` |

- **证据**：【亲测】`UsvTrackingEnv(path_type="straight")` 读出的就是代码默认值
- **后果**：【亲测】`test_step_contract` **28/40 概率失败**（`psi_err` 提前终止 → 测试调 `reset()` → `info` 里没有 `applied_thrust` → `KeyError`）；全套 `pytest tests/ -q` 得 **52 passed, 1 failed**
- **另一后果**：【复核】同一 LOS 控制器，用代码默认跑随机路径 16/30 成功（14 次超时），用 env.yaml 跑 30/30

### D8 · DR 覆盖不全

- **证据**：【代码核实】19 个水动力参数中 **5 个恒为 0**（`Yr_dot`、`Yr`、`Nv`、`Yrr`、`Nvv`），乘性扰动改不动它们 → 实际只覆盖 **14/19**
- **且完全没有**：风/流/浪扰动、推力增益或失效、传感器偏置或相关 GPS 误差
- **影响**：`README` 的"DR ±20%"表述会让读者高估鲁棒性覆盖

### D9 · `t_lag` 无上界，存在失控模式

- **文件**：`envs/usv_tracking_env.py:253-271`
- **机制**：`t_eff` 一旦 clamp 到 0，`v_ref[0] = v_eps = 0.05`，而 `vr` 下限 0.1，导致 `t_lag` 每步按沿迹亏空的 ~10 倍增长
- **证据**：【复核】一个 beeline episode 把 `t_lag` 推到约 **16200 s**（4.5 小时虚拟滞后）
- **影响**：数值上不会崩，但语义上参考时间已无意义

### D10 · `failure_penalty = -10` 是死代码

- **文件**：`envs/usv_tracking_env.py:230-231, 352-365`
- **机制**：只有"terminated 且 reason≠success"才罚；`early_termination=false` 时没有任何违规会 `terminated=True`
- **影响**：奖励不对称（`success_bonus=+10` 活着，`-10` 永远走不到）

### D11 · `evaluate.py` 会静默错评 v1~v3

- **机制**：v1~v3 的 checkpoint 动作空间是 `Box(-25,25)`，v4/v5 才是 `Box(-1,1)`；CLI 无任何动作空间校验
- **证据**：【亲测】解包确认动作空间差异
- **影响**：拿现在的 CLI 跑老 checkpoint 会得到约 15 m 的荒谬 `e_ct`，且不报错 → 历史版本数字不可比

### D12 · `best/best_model.zip` 没有配套 `vecnormalize.pkl`

- **机制**：`EvalCallback` 未开 `save_vecnormalize`（`train.py:157-165`），只有 `CheckpointCallback` 和阶段结束才存统计
- **证据**：【亲测】`artifacts/rl_models/v5/best/` 只有一个 `best_model.zip`
- **影响**：教程第 968 行建议"部署一般用 best"——照做会**静默用错归一化统计**

### D13 · 部署包在当前树里无法构建/测试

- **证据**：【亲测】
  - `usv_mpc_ws/install/usv_rl_ros/lib/usv_rl_ros/` 只有 `rl_policy_node` 脚本，**没有 python 模块目录**

- **影响**：文档中"28 项部署契约测试通过"是 **2026-10-03 的历史证据**，不是当前树的属性

### D14 · 文档写的测试命令跑不通

### 8.2 若要往论文方向走，还缺什么

按顺序，缺一样都不可：

1. **强基线**：调参后的 LOS，或方案B（CTE 0.1007 已占先）
2. **多种子方差**：至少 5 个训练种子，报告均值±标准差
3. **消融**：至少验证"空间项 q=100"和"进度项 w=15"各自的边际贡献
4. **假设**：一句可证伪的话，例如"在同等观测信息下，RL 的航向误差优于最优 LOS，且能耗不超过其 2 倍"
5. **新颖性检验**：目前没有任何 PPO 相关的新颖性实验设计
6. **sim-to-sim 量化**：把 VRX 记录的 state+thrust 序列回放进 `usv_rl.dynamics.py`，报告逐轴一步预测残差

**在 1~3 完成之前，任何"PPO 优于 X"的表述都不应出现在对外材料里。**
